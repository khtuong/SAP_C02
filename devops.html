1. CI/CD Fundamentals & Pipeline Troubleshooting

Q1 What is the difference between Continuous Integration, Continuous Delivery, and Continuous Deployment?

Answer

  • Continuous Integration (CI): Developers merge code to a shared branch frequently (multiple times per day). Each merge triggers an automated build and test pipeline. The goal is to catch integration bugs early and keep the main branch always in a known-good, buildable state.
  • Continuous Delivery (CD): Every commit that passes CI is automatically prepared into a deployable artifact and promoted through environments (dev → staging). The release to production is still gated by a human (manual approval).
  • Continuous Deployment: Every commit that passes the full pipeline (including automated tests, integration tests, security scans) is automatically released to production without manual approval. This requires very high test confidence, feature flags, automated rollbacks, and strong observability.

Key insight: Most companies say "CI/CD" but actually do Continuous Delivery. True Continuous Deployment is a maturity level few teams reach because it requires deep investment in testing, canaries, and rollback automation.

Q2 A CI build that passed yesterday is failing today with no code changes. How do you investigate?

Answer

"Worked yesterday, broken today, no code change" almost always means an external dependency drift. Investigate the build environment, not the application code.

Investigation Steps

  1. Compare the failed run with the last green run — same commit SHA? Same agent/runner image? Same toolchain versions?
  2. Check dependency lockfiles — was the project resolving versions dynamically (^1.2.0, latest, :latest Docker tag)? A transitive package may have published a new release.
  3. Inspect the base image — pipelines using node:18 or python:3.11 get rebuilt as the upstream image is updated; a security patch may have changed glibc, OpenSSL, or Node minor version.
  4. Check the CI runner/agent — GitHub Actions and GitLab Runner rotate Ubuntu images monthly. A tool you depended on may have been removed or moved paths.
  5. Verify external services — package registry outages (npm, PyPI), artifact repo credentials expired, OIDC tokens for cloud login changed.
  6. Look at the failure signature — is it a network timeout, a missing binary, a TLS error, or a real test assertion? That tells you whether the cause is the environment or the code.

Immediate Mitigation

  • Pin the runner image to the version that worked (e.g., ubuntu-22.04 instead of ubuntu-latest).
  • Pin Docker base image with a digest: FROM node:18@sha256:....
  • Restore the lockfile from the last green build if dependencies were resolved fresh.

Long-Term Prevention

  • Always commit lockfiles and use frozen-install modes: npm ci, pip install -r requirements.txt --require-hashes, go mod download.
  • Pin base image digests in production Dockerfiles.
  • Use a private artifact mirror (Artifactory, Nexus, ECR pull-through cache) so upstream changes don't propagate instantly.
  • Add a daily scheduled build on main to detect environment drift before a developer notices.
Q3 What strategies do you use for fast and reliable pipelines?

Answer

  • Cache aggressively, but explicitly — cache ~/.m2, ~/.npm, node_modules, Docker layer caches. Use a cache key tied to the lockfile hash so stale caches don't poison builds.
  • Parallelize independent jobs — unit tests, linting, security scans, and container builds can run concurrently. Reserve sequential stages only for true dependencies (build → integration test → deploy).
  • Fail fast — run cheap, high-signal checks first (linters, type checks, unit tests). Don't waste 20 minutes on integration tests when a syntax error would have caught the issue.
  • Split slow tests — shard test suites across runners. Most frameworks support this (pytest-split, jest --shard, Go test -parallel).
  • Use ephemeral runners — fresh environment per build prevents "state leak" but pre-warm a base image to avoid 5 minutes of bootstrap.
  • Build once, promote everywhere — produce a single immutable artifact in CI; deploy that same artifact to dev, staging, and prod. Never rebuild per environment.
  • Quarantine flaky tests — don't ignore them; tag them and track flake rate, but stop them from blocking the pipeline.
Q4 A deployment pipeline succeeded but the new version is not running. How do you debug?

Answer

This is one of the most common silent failures. The pipeline reports "deploy succeeded" but the actual workload is still on the old version. The pipeline lied to you (or you lied to the pipeline).

Investigation Steps

  1. Confirm what "deployed" means — did the pipeline only push the image, or did it actually trigger a rollout? docker push succeeding is not the same as kubectl apply succeeding is not the same as pods being healthy on the new version.
  2. Verify the image tag — if the manifest references :latest and imagePullPolicy: IfNotPresent, the node may keep using the cached old image. Tag immutably (SHA, semver) and prefer imagePullPolicy: Always for moving tags.
  3. Check the rollout status — kubectl rollout status deployment/myapp. Look for stuck pods, ImagePullBackOff, or CrashLoopBackOff on the new replica set.
  4. Inspect the deployed pod's image — kubectl get pod -o jsonpath='{.spec.containers[*].image}'. Don't trust the manifest; trust the running container.
  5. Check for HPA, PDB, or admission controllers blocking the rollout silently.
  6. Validate the deployment target — was it deployed to the right cluster, namespace, region, or account? Pipeline misconfigurations frequently deploy to "dev" while claiming success on "prod".

Immediate Mitigation

  • Force a rollout: kubectl rollout restart deployment/myapp.
  • If image cache is the issue: change the tag to an immutable digest.

Long-Term Prevention

  • Use immutable image tags (commit SHA or semver), never latest in production.
  • Pipeline must wait for rollout status with a timeout and fail if not healthy.
  • Smoke-test post-deploy: hit /healthz and verify the build SHA in the response matches the deployed SHA.

Useful Commands

kubectl rollout status deployment/myapp -n prod --timeout=5m
kubectl get rs -n prod -l app=myapp
kubectl describe deployment myapp -n prod
kubectl get pods -n prod -l app=myapp -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.containers[*].image}{"\n"}{end}'
curl -sf https://myapp.example.com/healthz | jq .version
Q5 How do you secure a CI/CD pipeline?

Answer

  • Secrets management: Never store secrets in code or env files committed to git. Use a secret manager (Vault, AWS Secrets Manager, GitHub OIDC for short-lived cloud credentials).
  • Least-privilege runners: Build runners should have only the IAM/RBAC permissions strictly needed for their stage. A test runner does not need prod push access.
  • OIDC instead of long-lived keys: Modern CI (GitHub Actions, GitLab) can exchange a short-lived OIDC token for AWS/GCP/Azure credentials. No static access keys.
  • Signed and verified artifacts: Sign container images with cosign/Sigstore; verify signatures at admission time in Kubernetes (cosign + Kyverno/Gatekeeper).
  • SBOM and vulnerability scans: Generate a Software Bill of Materials, scan with Trivy/Grype/Snyk, fail builds on critical CVEs.
  • Branch protection: Require PR reviews, status checks, and signed commits for the main branch. Disallow force pushes.
  • Audit logs: Every deployment must be traceable to a commit, a user, and a timestamp.
  • Pinned actions: Reference third-party CI actions by full SHA, not version tag — a tag can be moved to malicious code.
Q6 What is the difference between blue/green, canary, and rolling deployments?

Answer

  • Rolling deployment: Replace pods/instances incrementally (e.g., 25% at a time). Lowest infra cost, simplest. Downside: both versions run simultaneously briefly; partial bad release can affect a fraction of traffic before detection.
  • Blue/Green: Run two full environments. "Blue" is live, "Green" is the new version. Cut over traffic at the load balancer once green is verified. Instant rollback (flip back to blue). Downside: 2× infrastructure cost during cutover.
  • Canary: Deploy the new version to a small slice of traffic (1%, 5%, 25%, 100%). Monitor SLIs at each step; auto-rollback if error rate or latency exceeds threshold. Best for production safety, requires good observability and traffic-splitting (Istio, Linkerd, ALB weighted target groups, Argo Rollouts).

When to use which:

  • Stateless web service with strong observability → canary.
  • Service with expensive warmup or schema changes → blue/green.
  • Simple internal service, low risk → rolling.
Q7 A pipeline succeeds in CI but fails when deploying to production. What are common causes?

Answer

  • Environment drift: CI runs on Ubuntu, prod is RHEL; CI uses Postgres 14, prod is 13; CI has 16GB RAM, prod node has 4GB.
  • Missing secrets or config: CI mocked secrets or used a test endpoint; prod doesn't have the new environment variable defined.
  • Network policies / firewall: Prod has stricter egress rules — the app cannot reach a new external API it talks to.
  • RBAC / IAM differences: The CI service account has broader permissions than the prod runtime account.
  • Database state: Migrations applied automatically in CI but production needs manual or sequenced migration.
  • Resource limits: Prod has CPU/memory limits, OOMKills happen under real load.
  • Image architecture mismatch: Built amd64 image, prod runs on arm64 (Graviton/M-series).
  • DNS / service discovery: Service names differ between environments; service mesh routing differs.

Mitigation principle: Make environments as identical as possible. Use the same infrastructure-as-code modules; only environment-specific variables should differ.

Q8 How do you handle database schema migrations in a CI/CD pipeline?

Answer

Database migrations are the single most dangerous part of any deployment because they are stateful and often irreversible.

  • Use migration tools: Flyway, Liquibase, Alembic, golang-migrate, Prisma Migrate. Never run ad-hoc SQL.
  • Expand-Contract pattern (Parallel Change):
    1. Expand: Add new columns/tables; keep old ones. Deploy code that writes to both old and new.
    2. Migrate data: Backfill new structure in batches.
    3. Switch reads: Deploy code that reads from new structure.
    4. Contract: After confidence period, remove old structure.
  • Migrations run before app deploy — so the new app version always sees the schema it expects, and the old app version still works against the new schema (because expand is backward-compatible).
  • Lock-free migrations: Avoid ALTER TABLE that rewrites the table on large tables. Use CREATE INDEX CONCURRENTLY on Postgres; use online schema change tools (gh-ost, pt-online-schema-change) on MySQL.
  • Always have a rollback strategy — for destructive migrations, take a backup first, or use blue/green with both schemas.
Q9 What is GitOps and what problem does it solve?

Answer

GitOps is the practice of using a Git repository as the single source of truth for declarative infrastructure and application configuration. A controller (ArgoCD, Flux) continuously reconciles the live cluster state with what's defined in Git.

Problems it solves:

  • Drift: Manual kubectl edit changes are reverted automatically by the reconciler — the cluster always matches Git.
  • Auditability: Every change is a Git commit, reviewed via PR, traceable to a person and time.
  • Disaster recovery: Rebuild a cluster by pointing a new controller at the same repo.
  • Security: CI doesn't need cluster credentials; the in-cluster controller pulls from Git. The blast radius of a compromised CI runner shrinks.
  • Rollback = revert commit.
Q10 What is "deployment vs release" and why does it matter?

Answer

  • Deployment: Putting new code on production infrastructure (the new binary is now running).
  • Release: Making the new feature visible/active to users.

Separating these — typically via feature flags — is a senior practice. You can deploy code daily but release features when business is ready. If a feature causes incidents, you flip the flag off without needing a redeploy. This decouples engineering velocity from product timing and reduces deploy-time risk to near zero for flagged code.

2. Production Incident Troubleshooting

Q11 Production is down. Walk me through the first 10 minutes.

Answer

  1. Acknowledge the alert — silence the page so duplicate notifications don't slow you down. Confirm you're the responder.
  2. Open an incident channel — Slack/Teams room, video bridge, incident doc. Everyone communicates there; nothing in DMs.
  3. Assess scope and severity — how many users? Which regions? Is data being lost? Is money being lost? This drives SEV level and who you wake up.
  4. Form the team — assign roles: Incident Commander (decision-maker), Comms lead (status page, stakeholders), Ops lead (drives technical investigation). Even a 1-person incident benefits from being explicit about which hat you're wearing.
  5. Stop the bleeding before debugging the cause. If a recent deploy is suspect → roll back. If a config change is suspect → revert. Don't try to fix-forward during the first 10 minutes unless you're certain.
  6. Communicate — public status page update within 5 minutes saying "we are investigating an issue". Internal update every 15–30 minutes.
  7. Preserve evidence — snapshot logs, save dashboards (URLs with time range), take heap/thread dumps before restarting anything you'll want to debug later.

Senior principle: Mitigation precedes diagnosis. Customers don't care why it broke; they care how fast it's working again.

Q12 How do you decide whether to roll back or fix-forward?

Answer

Default: roll back. Rollback is fast, reversible, and well-understood. Fix-forward should be the exception, not the rule.

Roll back when:

  • A recent deploy correlates strongly with the incident start time.
  • Rollback is a known safe operation (previous version was healthy).
  • No irreversible state changes (DB migrations) have happened.

Fix forward when:

  • Rollback is impossible (an irreversible migration, schema change, or data backfill already happened).
  • The fix is trivial, tested, and the path to deploy is faster than rollback.
  • The previous version has a known critical bug that's worse than the current one.

Hard rule: If you cannot articulate the fix in one sentence and you're under time pressure, roll back.

Q13 A customer reports the website is slow. How do you investigate?

Answer

Investigation Steps (top of the stack to bottom)

  1. Quantify "slow" — what page? What region? What time? How slow (latency number)? Use customer's request ID/trace ID if available.
  2. Check from outside — synthetic monitoring (Pingdom, Datadog Synthetics) or just curl from multiple regions. Determine if it's global or regional.
  3. Inspect golden signals dashboards — latency (p50, p95, p99), traffic, errors, saturation (the USE/RED methods).
  4. Check the CDN layer — CloudFront/Akamai cache-hit ratio dropped? Edge errors?
  5. Check the load balancer — increased 5xx, slow backends, unhealthy targets?
  6. Check application metrics — request rate, error rate, GC pauses, thread pool exhaustion, queue depth.
  7. Check the database — slow query log, lock waits, replication lag, connection pool saturation.
  8. Check downstream dependencies — third-party APIs slow? Trace spans will show.
  9. Check infrastructure — CPU throttling, disk IO saturation, network packet loss, noisy neighbors.

Useful Commands

# From the edge
curl -w "@curl-format.txt" -o /dev/null -s https://example.com/

# Application traces (look at p99 spans)
# Datadog / Honeycomb / Tempo — search for slow traces

# Database (Postgres)
SELECT pid, now() - query_start AS duration, query
FROM pg_stat_activity
WHERE state = 'active'
ORDER BY duration DESC LIMIT 10;

# Kubernetes — CPU throttling
kubectl top pods -n prod --sort-by=cpu
kubectl get --raw /api/v1/nodes/<node>/proxy/metrics/cadvisor | grep throttled
Q14 Half of your API requests are returning 5xx. Where do you look first?

Answer

  1. Confirm "half" — is it 50% randomly, or 100% from one client / region / version? Check the breakdown by status code, endpoint, version, and host.
  2. Look at the load balancer breakdown by target — if 5 backends out of 10 are unhealthy, you'll see ~50% error rate. Could be one bad AZ, one bad node, one bad pod replica that didn't get drained.
  3. Look at the deployment timeline — was a rolling deploy in progress? You might have half the pods on a broken version.
  4. Check pod readiness — are some pods passing liveness but failing readiness? They might be getting traffic they can't handle.
  5. Check connection pools to dependencies — DB pool exhausted on some pods, healthy on others.

Immediate Mitigation

  • Drain or terminate the bad pods/instances.
  • Roll back the in-progress deploy if it correlates.
  • Shift traffic away from the bad AZ if it's localized.
Q15 Disk on a production server is 95% full. What do you do?

Answer

Investigation Steps

  1. Identify the consumer — df -h to find the affected filesystem, then du -h --max-depth=1 / drilling down.
  2. Common culprits: /var/log (logrotate broken), application dumps, Docker overlay layers, /tmp, database WAL files, backup files, old kernels in /boot.
  3. Check for deleted-but-open files — lsof | grep deleted. A process holding a deleted file still consumes space until restarted.

Immediate Mitigation

  • Truncate or rotate large log files: truncate -s 0 /var/log/huge.log (be careful — only if the writer reopens).
  • Clean Docker: docker system prune -af --volumes.
  • Clean package cache: apt clean, yum clean all.
  • Restart the process holding deleted file handles.
  • If on cloud, expand the volume (EBS modify, GCP resize) and grow the filesystem (resize2fs, xfs_growfs).

Long-Term Prevention

  • Configure logrotate with compression and retention.
  • Ship logs off-box (Loki, ELK, CloudWatch); don't keep them on the app server.
  • Add disk usage alerts at 70%, 85%, 95%.
  • Use ephemeral storage (containers, immutable instances) so disk fills can't accumulate.

Useful Commands

df -hT
du -h --max-depth=1 /var | sort -hr | head -20
sudo lsof +L1                       # files with link count 0 (deleted but open)
sudo find / -type f -size +500M 2>/dev/null
journalctl --vacuum-time=2d
docker system df
docker system prune -af --volumes
Q16 One service is causing cascading failures across the system. How do you contain it?

Answer

A cascade happens when a slow/failing service exhausts callers' resources (threads, connections, retries), which then fail their own callers. The system becomes saturated even though only one component is broken.

Containment (in order)

  1. Shed load on the failing service — rate limit, drop non-essential requests, return cached responses.
  2. Open a circuit breaker on its callers — fail fast instead of waiting. Hystrix, Resilience4j, Istio outlier detection.
  3. Disable retries temporarily — retries during an incident multiply load and worsen the cascade.
  4. Isolate via bulkheads — give each downstream its own thread pool/connection pool so it can't exhaust the shared pool.
  5. Scale the failing service horizontally — only if the issue is capacity, not a code bug.
  6. Disable the broken feature via feature flag if the service is non-critical.

Long-Term Prevention

  • Every cross-service call must have a timeout, a retry budget, and a circuit breaker.
  • Implement load shedding at the edge.
  • Capacity-test for partial-failure scenarios, not just full-load.
  • Build graceful degradation paths — return stale data or empty results rather than 500.
Q17 An incident is ongoing and stakeholders keep asking for ETAs. How do you handle communication?

Answer

  • Have a dedicated Comms Lead — separate from the people debugging. Engineers can't fix problems while answering executive DMs.
  • Update on a fixed cadence — every 15 or 30 minutes regardless of progress. "Still investigating, will update at 14:30" is a valid update.
  • Never promise an ETA you don't have. Say "we'll know more after X step", not "30 minutes". A missed ETA destroys trust.
  • Use a consistent template: What's the impact (users, regions, features), what's the current status (investigating / mitigating / monitoring / resolved), what's the next step, when's the next update.
  • One source of truth — status page for external, single Slack thread or incident doc for internal. Don't fragment.
  • Resist the temptation to silence the channel — even if 50 people are watching, that's fewer DMs and questions for the responders.
Q18 The previous on-call left no documentation and a recurring alert keeps firing. What do you do?

Answer

  1. Don't blindly silence it. Treat the absence of context as a red flag — there's a reason this alert exists.
  2. Reverse-engineer the alert — read the Prometheus rule / Datadog monitor definition. What does it actually measure? What's the threshold? Why was that threshold chosen (often you'll find a clue in commit history)?
  3. Check historical firing pattern — does it fire every Monday at 9 AM (batch job)? Every full moon (cron edge case)? Or randomly?
  4. Correlate with logs/metrics at the firing time — find what was actually anomalous.
  5. Decide: real alert needing fix, or noisy alert needing tuning?
  6. Write the runbook you wished you had — even if it's just "as of YYYY-MM-DD, this alert is suspected to be X; investigation TBD."

Senior practice: Every alert should have a runbook link in the alert payload. If yours don't, that's a process gap to raise, not a personal burden.

3. Investigation Methodology

Q19 Describe a structured methodology for investigating a production issue.

Answer

I follow a layered, hypothesis-driven approach. The key is to be explicit about what you're testing and to write it down so the team isn't running in circles.

  1. Define the symptom precisely. "API is slow" → "p99 latency on POST /orders went from 200ms to 4s at 14:23 UTC, only in eu-west-1".
  2. Establish a timeline. When did it start? What changed within ±1 hour? Deploys, config pushes, feature flag flips, infrastructure changes, traffic spikes.
  3. Form hypotheses. List 3–5 possible causes ranked by likelihood. Don't tunnel-vision on the first one.
  4. Disprove cheaply. Pick the hypothesis that's fastest to confirm/deny. If it's deploy-related, check the deploy log first — it's a 30-second check.
  5. Use the data, not your gut. Metrics → logs → traces → live debugging, in that order of cost.
  6. Bisect. If something started at T, find a "good" point before T and a "bad" point after, then bisect — works for commits, configs, traffic patterns.
  7. Always look at correlation across the stack. The first metric that breaks is often a symptom, not the cause.

The USE method (for resources): Utilization, Saturation, Errors.
The RED method (for services): Rate, Errors, Duration.
Combine both: USE for nodes/disks/network, RED for services.

Q20 How do you avoid "shotgun debugging" during an incident?

Answer

Shotgun debugging is making random changes hoping something works. It's dangerous because:

  • You destroy evidence.
  • You can't tell which change fixed the problem (so you can't reproduce or prevent recurrence).
  • You can make the incident worse.

Discipline:

  • Before making a change, state the hypothesis: "I think the DB connection pool is exhausted, so I'm restarting the app to clear it."
  • Make one change at a time and wait long enough to observe the effect.
  • Document every change in the incident channel with a timestamp.
  • If multiple people are typing commands, designate one driver. Others suggest; the driver executes.
Q21 What is the "Five Whys" technique and when do you use it?

Answer

"Five Whys" is asking "why?" repeatedly to push past the surface symptom to the underlying cause. It's primarily used in post-incident review, not during the incident.

Example:

  • The site went down. Why?
  • The deployment broke the API. Why?
  • A null pointer exception happened on every request. Why?
  • A new field was missing from the database. Why?
  • The migration hadn't been run in production. Why?
  • The pipeline didn't enforce migration-before-deploy ordering.

The "fix" at level 2 (revert the deploy) would prevent today's outage. The fix at level 5 (enforce ordering in the pipeline) prevents the class of outage.

Caveat: Don't take "five" literally. Stop when you reach an actionable systemic cause. And avoid stopping at "human error" — humans operate the system; the system should make the error hard to commit.

Q22 A metric spiked but nothing seems wrong to users. Do you investigate?

Answer

Yes — but with calibrated urgency. A metric anomaly with no user impact may be:

  • A leading indicator (queue depth growing, soon to overflow).
  • A broken metric (instrumentation bug — important to know so you don't get blindsided later).
  • A benign change (a new deploy uses a different code path; metric pattern shifts but performance is fine).
  • A silent failure (background job stopped running; users won't notice until later).

Treat it as a P3/P4 investigation, not a page-everyone incident. But always close the loop — either fix the issue, fix the metric, or update the runbook to say "this spike is expected because X".

Q23 How do you investigate an issue you can't reproduce?

Answer

  1. Increase observability first. Add structured logging, traces, and metrics around the suspected code path. Deploy. Wait for it to happen again with more data.
  2. Look at the differences. What's true for users who see it that isn't true for users who don't? Browser, region, account age, feature flag exposure, request shape.
  3. Capture state at failure time. Heap dumps, thread dumps, packet captures, request/response payloads, full traces. Make sure these are saved persistently so you can look at them later.
  4. Replay traffic. Capture production requests (Goreplay, Envoy tap) and replay them in a staging environment.
  5. Use canaries. Deploy more verbose logging to 1% of traffic to reduce log volume.
  6. Resist the urge to declare "not reproducible" and close the ticket. Customers don't experience "not reproducible"; they experience the bug.
Q24 What's your approach when logs are missing the information you need?

Answer

  • Add the logs and redeploy — for non-critical incidents this is fine; verbose logs at INFO temporarily, then dial back.
  • Use higher-level signals — traces often show what logs don't (parent/child spans, durations, attributes).
  • Tap the live process — strace, tcpdump, perf, jstack/py-spy/rbspy can give you runtime state without redeploy.
  • Profile in production — pyroscope, parca, continuous profiling. Looking at flame graphs of the live process often reveals the issue.
  • After the incident — file a follow-up to add the missing logs as part of the action items. "I couldn't see X" is a legitimate gap to fix.

4. Impact Reduction & Mitigation

Q25 What is "stop the bleeding" and why does it matter more than finding the root cause?

Answer

"Stop the bleeding" means: take the fastest action that reduces user impact, even if it doesn't fix the underlying bug. The longer customers are affected, the more harm — financial, reputational, contractual — accumulates.

A 5-minute mitigation that takes the system from "broken for everyone" to "working with a degraded feature" beats a 2-hour debugging session that finds the perfect root cause.

Common bleeding-stoppers:

  • Roll back the recent deploy.
  • Flip the feature flag.
  • Route traffic away from the bad region.
  • Scale up horizontally.
  • Restart the misbehaving process.
  • Block the abusive client.
  • Drop non-essential traffic.

Root cause comes after. Once mitigation is in place, you can investigate calmly without customers watching.

Q26 What is "graceful degradation" and how do you design for it?

Answer

Graceful degradation means the system continues to provide partial functionality when a dependency fails, rather than failing entirely.

Examples:

  • An e-commerce checkout still works if the recommendation engine is down — just no "you might also like" section.
  • If real-time inventory is unavailable, show cached inventory with a "stock may be inaccurate" notice instead of an error.
  • If authentication is slow, allow read-only access to logged-out content.

Design patterns:

  • Circuit breakers stop calling failing dependencies and return a fallback.
  • Fallback responses — empty arrays, cached values, "service unavailable" UI elements.
  • Asynchronous patterns — queue the work, respond optimistically, retry later.
  • Feature flags for non-critical features so you can disable them without redeploy.
  • Tiered functionality — core paths (checkout, login) are isolated from optional paths (analytics, recommendations).
Q27 What is load shedding and when do you use it?

Answer

Load shedding is intentionally rejecting some requests when the system is overloaded, to ensure the rest succeed. Without shedding, an overloaded system slows down all requests, often causing all of them to time out — much worse than failing some.

Strategies:

  • Rate limiting per user/IP/API key.
  • Priority-based shedding — drop low-priority requests (analytics, background sync) first; protect high-priority (checkout, login).
  • Adaptive concurrency limits (Netflix's concurrency-limits, Envoy's adaptive concurrency) — automatically reject when in-flight requests exceed a learned threshold.
  • Queue depth limits — reject when the request queue exceeds N.
  • 503 with Retry-After — tell clients to back off and try later.

Key insight: A clean fast 503 is better than a slow timeout. Failure is acceptable; unresponsiveness is not.

Q28 A single tenant is overloading your shared infrastructure. How do you isolate them?

Answer

Immediate Actions

  • Identify the noisy tenant via request logs / API key analytics.
  • Apply a per-tenant rate limit at the gateway.
  • If they have a clearly anomalous traffic pattern (1000× normal), temporarily block them while you talk to them.

Long-Term Prevention (multi-tenancy patterns)

  • Per-tenant quotas at the API layer (requests per second, requests per day, data volume).
  • Bulkheads — give large tenants dedicated worker pools/queues so they can't starve others.
  • Cell-based architecture — shard tenants across isolated "cells" (groups of services + DB). A bad tenant only affects their cell.
  • Cost-based throttling — limit by computed cost (CPU seconds, DB rows scanned), not just request count.
  • Separate critical-path dependencies — read replicas, queue partitions, cache namespaces per tenant tier.
Q29 What is a "retry storm" and how do you prevent it?

Answer

A retry storm occurs when many clients simultaneously retry failed requests, multiplying load on an already-struggling backend. The retries can be more harmful than the original failures.

Prevention:

  • Exponential backoff with jitter. Without jitter, clients all retry at the same intervals after a shared incident; jitter randomizes timing.
  • Retry budgets — cap retries to a percentage of base traffic (e.g., 10%). If 50% of requests are failing, retries can't make total traffic >1.1× base.
  • Don't retry non-idempotent operations unless you have an idempotency key.
  • Respect Retry-After headers — the server is asking you to slow down; obey it.
  • Circuit breakers — when failures spike, stop calling for a cooldown period instead of retrying.
  • Failure-class-aware retries — retry transient errors (network blip, 503), not deterministic ones (400, 401, 404).
Q30 Your primary region went down. How do you fail over?

Answer

The hardest part of failover isn't the failover itself — it's making sure the secondary region is actually ready.

Steps

  1. Verify the secondary's health. Is the standby region taking traffic in normal canary load? Is its data current (replication lag)?
  2. Check data consistency. If async replication, you'll lose some recent writes. Is the business OK with that? For some systems (financial), it may be better to wait for the primary than to fail over and lose data.
  3. Update DNS/routing — change Route53 health check / Global Load Balancer weight to send traffic to secondary. Be aware of DNS TTL — clients may cache the old endpoint for the TTL duration.
  4. Promote replicas to primary in the secondary region (e.g., RDS read replica → standalone).
  5. Disable writes in the failed region to prevent split-brain when it comes back.
  6. Communicate. Internal stakeholders need to know you've failed over; some features may behave differently (eventual consistency, missing data).

Long-Term Prevention

  • Practice failover regularly (game days, chaos engineering).
  • Automate health-based failover where data loss tolerance permits.
  • Run active-active for stateless workloads so failover is just a load balancer change.
  • Document RPO (recovery point objective) and RTO (recovery time objective) and verify them via drills.

5. Root Cause Analysis

Q31 What makes a good post-incident review (postmortem)?

Answer

  • Blameless culture. Focus on systems and processes, not individuals. Humans operate complex systems; if a single mistake can take production down, the system has a flaw.
  • Detailed timeline. Minute-by-minute: when the issue started, when it was detected, when it was acknowledged, every action taken, when impact ended, when "all clear" was declared.
  • Impact statement. Quantify: how many users, how long, what features, estimated revenue loss, SLO budget consumed.
  • Contributing factors (not "root cause" — incidents usually have multiple).
  • What went well. Don't only list mistakes; the team did things right (fast detection, good comms, clean rollback). Reinforce those.
  • Action items with owners and due dates. Each one tracked to completion. Action items without owners are not real.
  • Lessons learned, shareable across the org so other teams benefit.

Anti-patterns: "Engineer ran wrong command" (blame). "We'll be more careful" (not actionable). "Add more tests" (vague). "Fixed already, no follow-up needed" (missed opportunity).

Q32 How do you distinguish root cause from contributing factors?

Answer

Modern SRE practice rejects the idea of a single "root cause" for non-trivial incidents. Real outages emerge from multiple contributing factors aligning (Swiss Cheese model). Examples:

  • A bug existed in code (factor 1).
  • Tests didn't cover the case (factor 2).
  • Canary didn't catch it because load was below the threshold (factor 3).
  • Alerting was on the wrong metric (factor 4).
  • The on-call had no runbook (factor 5).

Calling any one of these the "root cause" obscures the systemic problems. A good RCA enumerates all factors and proposes mitigations across them. Defense in depth matters because any single layer can fail.

Q33 What is a "blameless" postmortem and why is it important?

Answer

Blameless means: when discussing what happened, assume everyone involved acted reasonably given the information they had at the time. Don't ask "why did Alice deploy that?" — ask "why did our process allow that deploy to reach production?".

Why it matters:

  • People hide mistakes if blame is the consequence. Incidents get reported late or not at all.
  • Engineers stop pushing risky changes — but speed is a competitive advantage.
  • The real systemic flaws stay hidden because everyone is busy defending themselves.

What blameless does NOT mean: there are no consequences for negligence. If someone repeatedly ignores safety practices, that's a performance conversation — but it happens outside the postmortem, not in it.

Q34 How do you ensure action items from postmortems actually get done?

Answer

  • Owner + due date per item. No "the team will do X". "Bob will complete X by Nov 15."
  • Tracked in the same system as other engineering work (Jira, Linear). Not in the postmortem doc that no one will revisit.
  • Prioritized by severity — items from a P1 should jump the queue.
  • Reviewed weekly by the SRE team or in incident review meetings. Surface stale items and either reprioritize, reassign, or explicitly accept the risk and close.
  • Tie to error budget. Teams that burn their error budget cannot ship new features until their action items are completed — strong forcing function.
  • Categorize them: detection (would we see this faster?), prevention (would the issue not have happened?), mitigation (would impact be smaller?), recovery (would we restore faster?). Each category needs items.
Q35 Walk me through a memorable incident you investigated and what you learned.

Answer (Template — adapt to your real experience)

A strong answer follows STAR (Situation, Task, Action, Result) and emphasizes learning, not heroics.

  • Situation: "We had a midnight P1 — checkout latency went from 300ms to 30s."
  • Task: "I was incident commander; I had to mitigate, then find why."
  • Action: Be specific about what you checked, in what order, and why. Mention false starts honestly — they show real experience. "I first suspected the DB, but the slow query log was clean. Then I noticed thread pool saturation, which pointed to a downstream call."
  • Result: Mitigated by [X] in N minutes. Root cause was [Y]. Post-incident actions [Z] were implemented.
  • Learning: What you now do differently as a result. This is the most important part — interviewers care that you've learned, not that you've never failed.

6. Kubernetes & Container Troubleshooting

Q36 A pod is in CrashLoopBackOff. How do you debug it?

Answer

Investigation Steps

  1. Describe the pod — kubectl describe pod <pod>. Look at Events at the bottom: ImagePullBackOff? OOMKilled? Liveness probe failing?
  2. Read the container logs — kubectl logs <pod> for current attempt, --previous for the last crashed instance.
  3. Check exit code — kubectl get pod <pod> -o jsonpath='{.status.containerStatuses[*].lastState.terminated.exitCode}'. Code 137 = OOMKilled (SIGKILL). Code 139 = segfault. Code 143 = SIGTERM.
  4. Resource limits — set too low? Check resources.limits.memory against actual usage.
  5. Probes — is liveness probe configured aggressively (e.g., 1s initial delay on a JVM app that takes 30s to start)? Pod will be killed before it's ready.
  6. ConfigMaps/Secrets — missing required env var or mounted file?
  7. Storage — PVC unbound, mount failing.
  8. For a stuck startup: override the command and shell in for live debugging.

Useful Commands

kubectl get pods -n prod
kubectl describe pod <pod> -n prod
kubectl logs <pod> -n prod --previous
kubectl logs <pod> -n prod -c <container> --since=10m

# Resource usage
kubectl top pod <pod> -n prod --containers
kubectl get pod <pod> -o yaml | grep -A3 resources

# Override command for debugging
kubectl debug -it <pod> --image=busybox --target=<container>
kubectl run -it debug --image=<same-image> --command -- sh

# Exit code lookup
kubectl get pod <pod> -o jsonpath='{range .status.containerStatuses[*]}{.name}{": exit="}{.lastState.terminated.exitCode}{"\n"}{end}'
Q37 What does ImagePullBackOff mean and how do you fix it?

Answer

The kubelet failed to pull the container image. Common causes:

  • Typo in image name or tag — most common. Verify with kubectl get pod -o yaml | grep image: and confirm the image exists in the registry.
  • Private registry without imagePullSecrets — kubectl create secret docker-registry and reference in the pod spec.
  • Wrong registry URL — ECR/GCR/ACR require fully qualified URLs and the correct region.
  • Auth token expired — for ECR, the helper or IRSA must refresh tokens.
  • Architecture mismatch — image is amd64-only, but the node is arm64 (or vice versa).
  • Rate limiting — Docker Hub limits anonymous pulls to 100/6h per IP. Use a pull-through cache or authenticated pulls.
  • Network — node can't reach the registry (NAT, security group, VPC endpoint).

Useful Commands

kubectl describe pod <pod> | grep -A10 Events
docker pull <image>    # from a node, replicate the issue
# Check architecture
docker manifest inspect <image> | grep architecture
Q38 A pod is OOMKilled. What's happening and how do you fix it?

Answer

OOMKilled means the container exceeded its resources.limits.memory and the Linux kernel killed it (exit code 137). The pod restarts and the cycle repeats if memory usage stays high.

Investigation

  1. Confirm OOMKill: kubectl describe pod → look for "OOMKilled" in Last State.
  2. Look at memory usage over time: Prometheus container_memory_working_set_bytes vs kube_pod_container_resource_limits.
  3. Is the limit too low, or is the app leaking memory? Look at trend: steady growth = leak; sudden spike = usage surge.
  4. For JVM apps: are heap settings consistent with the container limit? -Xmx4g in a 4GB container leaves no room for off-heap, metaspace, native memory. Modern JVMs respect cgroup limits (-XX:+UseContainerSupport) but you should still leave headroom.
  5. For Go apps: GOMEMLIMIT tells the runtime to GC more aggressively before hitting the cgroup limit.

Mitigation

  • Increase memory limit if usage is legitimately higher than allocated.
  • If it's a leak, restart pods regularly while you fix the leak.
  • Profile in production (jmap, pprof) to find the leak.

Prevention

  • Set requests and limits based on observed usage, not guesswork. Use VPA recommendations.
  • Monitor memory pressure as an SLI.
  • Add OOMKill alerts.
Q39 A pod is stuck in Pending state. Why?

Answer

Pending means the scheduler hasn't placed the pod on a node, or the node hasn't started the container yet.

  • Insufficient cluster resources — no node has enough CPU/memory for the pod's requests. Check kubectl describe pod Events for "0/X nodes are available".
  • NodeSelector/Affinity/Taints — pod requires a node label/toleration that no node matches.
  • PVC pending — pod needs a PersistentVolumeClaim that hasn't been bound.
  • Image pulling — pod scheduled but kubelet still pulling image (large image, slow network).
  • Pod Disruption Budgets / quotas — namespace ResourceQuota or LimitRange blocking creation.

Useful Commands

kubectl get pod <pod> -o wide
kubectl describe pod <pod>
kubectl get nodes -o custom-columns=NAME:.metadata.name,CPU:.status.allocatable.cpu,MEM:.status.allocatable.memory
kubectl describe node <node> | grep -A5 'Allocated resources'
kubectl get pvc -n <ns>
kubectl get events -n <ns> --sort-by='.lastTimestamp'
Q40 A node is NotReady. What do you check?

Answer

  1. kubectl describe node <node> — look at Conditions: MemoryPressure, DiskPressure, PIDPressure, NetworkUnavailable.
  2. SSH to the node (if you can). Check:
    • systemctl status kubelet — is kubelet running?
    • journalctl -u kubelet -n 200 — kubelet errors (often: cgroup, certificate, container runtime).
    • systemctl status containerd (or docker) — container runtime healthy?
    • df -h — disk full? /var/lib/containerd or /var/lib/docker filling up is common.
    • dmesg | tail — kernel issues, OOM kills, network drops.
  3. From a healthy node or admin pod: can you reach the node's network? Security group, VPC routing.
  4. Has the kubelet certificate expired? Common on long-lived nodes.
  5. For managed clusters (EKS/GKE/AKS), check cloud console for instance status, autoscaler events, spot termination notices.

Mitigation

  • Cordon the node: kubectl cordon <node> (prevent new pods).
  • Drain it: kubectl drain <node> --ignore-daemonsets --delete-emptydir-data.
  • Replace it. For cloud-managed nodepools, often easier to terminate and let the autoscaler replace.
Q41 What's the difference between liveness, readiness, and startup probes?

Answer

  • Liveness probe: "Is the container alive?" If it fails, kubelet kills and restarts the container. Use when a deadlock or stuck process needs a restart. Be careful — too-aggressive liveness probes cause restart loops.
  • Readiness probe: "Is the container ready to serve traffic?" If it fails, the pod is removed from Service endpoints (no traffic) but not restarted. Use for warmup, dependency checks, or temporary unavailability.
  • Startup probe: "Has the container finished starting up?" Runs first; liveness/readiness don't start until startup succeeds. Use for slow-starting apps (JVM, large datasets to load) to avoid liveness killing them during boot.

Senior tips:

  • Liveness should probe something only a restart fixes (deadlock). Don't probe DB connectivity here — DB issues shouldn't restart your app.
  • Readiness can probe dependencies, but be careful of cascading: if every pod marks itself NotReady when the DB blips, your service drops to zero replicas.
  • Use startup probes for any app that takes >10–20s to start.
Q42 Two pods in the same cluster cannot communicate. How do you debug?

Answer

  1. DNS first — can pod A resolve pod B's Service name? kubectl exec -it <podA> -- nslookup <service>. Check kube-dns/CoreDNS pods are healthy.
  2. Service endpoints — kubectl get endpoints <service>. Empty? Selector doesn't match any pod's labels.
  3. NetworkPolicy — is there a NetworkPolicy denying ingress to B or egress from A? kubectl get networkpolicy -n <ns>.
  4. Direct pod IP — try curl <podB-IP>:<port> from pod A. If pod IP works but Service doesn't, the issue is at the Service layer.
  5. CNI — Calico, Cilium, Flannel — is the CNI agent running on both nodes?
  6. kube-proxy — for ClusterIP traffic, kube-proxy must be healthy on the source node.
  7. Cross-node — security group / firewall blocking node-to-node traffic on the CNI overlay ports?

Useful Commands

  nslookup <service>

Q43 What is the difference between a Deployment, StatefulSet, and DaemonSet?

Answer

  • Deployment: Manages stateless replicas. Pods are interchangeable; any can be killed and replaced. ReplicaSet underneath. Pod names random. Good for web servers, APIs, workers.
  • StatefulSet: Manages stateful, identity-bound pods. Each pod has a stable name (app-0, app-1), stable network identity (DNS), and stable storage (per-pod PVC). Ordered start/stop. Good for databases, queues with leader election, anything where pod identity matters.
  • DaemonSet: Ensures one (or one per matching label) pod runs on every node. Used for node-local agents: log collectors (Fluentd), node exporters, CNI agents, security daemons.
Q44 Your kubelet is filling the node's disk. What's likely going on?

Answer

Common culprits on a Kubernetes node:

  • Container logs in /var/log/containers or /var/lib/docker/containers — verbose application logging without log rotation. Container runtime should rotate (containerd's max_size), but config drift happens.
  • Container image cache — old images that aren't garbage-collected. Kubelet has imageGCHighThresholdPercent (default 85%).
  • EmptyDir volumes — pods writing to ephemeral storage without limits.
  • Crash dumps / core files from misbehaving apps.
  • Journald — system logs without retention policy.

Useful Commands

sudo du -h /var/lib/containerd --max-depth=2 | sort -hr | head
sudo du -h /var/log --max-depth=2 | sort -hr | head
crictl images       # or: docker images
crictl rmi --prune  # remove unused
sudo journalctl --vacuum-size=500M
Q45 How does the Horizontal Pod Autoscaler work, and when does it not?

Answer

HPA polls metrics (CPU by default, or custom metrics via metrics-server / Prometheus adapter) every 15s, computes the desired replica count, and scales the Deployment/StatefulSet.

Common failure modes:

  • metrics-server not installed or broken (kubectl top doesn't work).
  • No resource requests set on the pod — HPA based on CPU % requires resources.requests.cpu as the denominator.
  • Wrong metric for the workload — CPU isn't useful for an I/O-bound workload. Use queue depth, request rate, or latency instead.
  • Cluster autoscaler not configured — HPA scales pods, but if there's no node capacity, pods stay Pending. You need both HPA + Cluster Autoscaler.
  • Scale-down cool-down — by default HPA waits 5 minutes before scaling down to prevent flapping. Tune via --horizontal-pod-autoscaler-downscale-stabilization.
  • Burst traffic faster than scaling — HPA reaction time is minutes. Use over-provisioning or KEDA with predictive scaling.

7. Cloud Infrastructure Troubleshooting

Q46 An EC2 instance is unreachable via SSH. What do you check?

Answer

  1. Instance status checks in EC2 console — System Status and Instance Status. Failed system status = AWS infra issue (stop/start to migrate hypervisor). Failed instance status = OS or boot issue.
  2. Security group — does it allow port 22 from your IP? Did your IP change (VPN, home reconnect)?
  3. NACL at the subnet level — stateless, must allow both inbound and outbound.
  4. Route table — subnet has an internet gateway route? Or are you connecting via bastion/SSM?
  5. Key pair — correct key for this instance? Permissions on the .pem file (chmod 400)?
  6. OS-level firewall (iptables, ufw) — could be blocking even if AWS lets traffic through.
  7. sshd service crashed? Check via Session Manager or instance reboot.
  8. Disk full — sshd can fail to start when / is full. Use the Get Instance Console Output / Screenshot from AWS console.

Useful Commands

ssh -vvv -i key.pem ec2-user@<ip>     # verbose for diagnostics
aws ec2 describe-instance-status --instance-ids i-...
aws ec2 get-console-output --instance-id i-... --output text
aws ssm start-session --target i-...   # bypass SSH

Pro tip: Configure SSM Session Manager as the primary access path so you don't depend on SSH/network availability.

Q47 An RDS database is slow. How do you investigate?

Answer

  1. CloudWatch metrics — CPU, FreeableMemory, ReadIOPS/WriteIOPS, DiskQueueDepth, DBConnections, ReplicaLag.
  2. Performance Insights — top SQL statements by load, wait events. This is the single most useful tool RDS provides.
  3. Slow query log — enable via parameter group; review queries running over threshold.
  4. Connection saturation — DBConnections close to max_connections? Add RDS Proxy or fix app-level pooling.
  5. Disk IOPS exhausted — gp2/gp3 burst credit exhausted? Increase provisioned IOPS or move to gp3 with explicit IOPS.
  6. Storage full — disk autoscaling enabled? Storage near full can degrade performance.
  7. Locking — query pg_stat_activity for blocked queries, pg_locks, or in MySQL SHOW ENGINE INNODB STATUS.
  8. Replica lag — if reads go to replicas and they're behind, application sees stale data and may retry.

Useful Commands (Postgres)

-- Currently active queries
SELECT pid, now() - query_start AS duration, state, query
FROM pg_stat_activity
WHERE state != 'idle'
ORDER BY duration DESC LIMIT 20;

-- Blocked queries
SELECT bl.pid AS blocked_pid, a.query AS blocked_query,
       kl.pid AS blocking_pid, ka.query AS blocking_query
FROM pg_locks bl
JOIN pg_stat_activity a ON a.pid = bl.pid
JOIN pg_locks kl ON kl.transactionid = bl.transactionid AND kl.pid != bl.pid
JOIN pg_stat_activity ka ON ka.pid = kl.pid
WHERE NOT bl.granted;

-- Table bloat / vacuum status
SELECT schemaname, relname, n_dead_tup, last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC LIMIT 10;
Q48 Application calls to an S3 bucket are slow or failing intermittently. What's going on?

Answer

  • Request rate — S3 supports 3,500 PUT/COPY/POST/DELETE and 5,500 GET/HEAD per prefix per second. High request rates against a single prefix can be throttled. Distribute across prefixes.
  • Network path — using public endpoint instead of VPC Gateway/Interface endpoint? NAT gateway bandwidth/cost issues, NAT exhausted.
  • Cross-region calls — bucket in us-east-1, app in eu-west-1 — every call is 80-100ms RTT.
  • Eventual consistency (rare for S3 now — strong read-after-write since 2020) — but list operations can still lag.
  • SDK retries hiding errors — enable SDK logging to see actual API calls and retries.
  • 5xx errors from S3 — usually transient; AWS recommends exponential backoff. Persistent 503 SlowDown = throttling.
  • IAM/Bucket Policy denials — some calls work, some don't, depending on the object key/action.
Q49 Your AWS bill spiked overnight. How do you find the cause?

Answer

  1. AWS Cost Explorer — group by service, then by region, then by usage type. Find the service with the spike.
  2. Cost and Usage Report (CUR) in Athena — granular query by tag, resource ID, account.
  3. Common culprits:
    • Data transfer (NAT gateway, cross-AZ, cross-region).
    • S3 request charges from a misconfigured app polling.
    • CloudWatch Logs ingestion from verbose logging.
    • Unused snapshots, EBS volumes, unattached EIPs.
    • Forgotten resources in non-default regions.
    • Compromised credentials running crypto mining.
  4. If unusual EC2 spend — check CloudTrail for RunInstances from unexpected users/IPs. Treat as a possible security incident.

Long-Term Prevention

  • Set AWS Budgets with alerts.
  • Use Cost Anomaly Detection.
  • Tag all resources with owner/project/environment for accountability.
  • Service Control Policies to restrict expensive services (e.g., GPU instances).
  • Regular cost reviews — make spend a shared engineering concern, not just finance's problem.
Q50 An ELB / ALB is returning 502 errors. What could cause this?

Answer

502 from an ALB means the load balancer couldn't get a valid response from the target.

  • Target keep-alive timeout shorter than ALB idle timeout (default 60s). ALB sends a request on a reused connection, target has just closed it → connection reset → 502. Fix: Set target keep-alive > ALB idle timeout. For Node.js: server.keepAliveTimeout = 65000; server.headersTimeout = 66000.
  • Target crashed mid-response. Application errors.
  • Target health check failing but still receiving traffic due to draining delay or race.
  • Target SSL/TLS misconfigured (if using HTTPS to target).
  • Response too large for ALB to buffer (uncommon — ALB streams).
  • Misbehaving proxy in front of the app inside the target sending malformed responses.

Useful Commands

# ALB access logs to S3 — query with Athena
SELECT request_url, target_status_code, elb_status_code, target_processing_time
FROM alb_logs
WHERE elb_status_code = '502'
ORDER BY time DESC LIMIT 100;
Q51 An Auto Scaling Group is not scaling out under load. Why?

Answer

  • Scaling policy not triggered — CloudWatch alarm threshold not crossed for required period. Check ASG Activity tab.
  • Max capacity reached — ASG can't exceed its max.
  • Subnet/AZ capacity — chosen instance type unavailable in the subnet's AZ. Spread ASG across multiple AZs and use mixed instance types.
  • Service quota — vCPU quota for the instance family at AWS account level.
  • Launch template/config errors — instances fail to launch (bad AMI, IAM issue, user data error). Check Activity log for failures.
  • Cooldown period active — ASG waits between scaling actions.
  • Health checks failing after launch — new instances added then immediately replaced, churning without growing capacity.

8. Monitoring, Logging, Metrics, Tracing & Observability

Q54 What's the difference between monitoring and observability?

Answer

  • Monitoring answers known questions about known unknowns. You've decided in advance: CPU > 80% is bad, latency > 1s is bad. You define dashboards and alerts to watch for those specific conditions.
  • Observability is the property of a system that lets you answer unknown questions about unknown unknowns. You can ask new, ad-hoc questions of your data without having to ship new code or change dashboards.

Monitoring is necessary; observability is more powerful. Modern observability rests on three pillars (metrics, logs, traces) but the goal isn't to have all three — the goal is to be able to investigate any question without redeploying.

Practical example: If you only have CPU and latency dashboards, you can answer "is the server overloaded?" but not "is the latency increase coming from one user agent or all?". Observability requires high-cardinality data (per-user, per-endpoint, per-tenant tags).

Q55 What are the "three pillars" of observability and when do you use each?

Answer

  • Metrics (Prometheus, Datadog metrics, CloudWatch). Time-series numeric data. Cheap to store, fast to query. Best for: dashboards, alerts, capacity planning, knowing that something is wrong.
  • Logs (Loki, Elasticsearch, CloudWatch Logs). Discrete events with context. Best for: detailed investigation, understanding what exactly happened in a specific request.
  • Traces (Jaeger, Tempo, Datadog APM, Honeycomb). Causally-linked spans across services. Best for: understanding where time is spent in a distributed call, finding the slow downstream.

Common flow: alert fires from metric → look at a dashboard to see scope → drill into a trace to find the slow service → look at logs for that service to see the error detail.

Modern view: the "three pillars" are an oversimplification. Real observability is one queryable dataset with high-cardinality tags. But for now, most teams have all three because tooling vendors specialize.

Q56 What are the "Four Golden Signals" and why?

Answer

From the Google SRE Book — the four most important signals for any user-facing service:

  1. Latency — how long does a request take? Distinguish successful vs. failed; track distributions (p50, p95, p99), not averages.
  2. Traffic — how much demand? Requests per second for an API, transactions per second for a DB, bytes/second for storage.
  3. Errors — rate of failed requests. Explicit (5xx, exceptions) and implicit (wrong content but 200 OK).
  4. Saturation — how "full" is the system? CPU, memory, IO, thread pool, queue depth — the resource closest to its limit.

If you can only afford four graphs, draw these. Most operational issues will show up in at least one.

For non-user-facing systems (queues, batch), use USE: Utilization, Saturation, Errors.

Q57 What is a histogram and why are averages misleading for latency?

Answer

Averages hide tail latency. Imagine 99 requests at 100ms and 1 at 5000ms — the average is 149ms, looks great. But 1% of users had a 5-second experience. That 1% might be your highest-value customers.

A histogram bins request latencies and lets you compute percentiles:

  • p50 (median) — typical experience.
  • p95 — what most users feel under load.
  • p99 — tail; outliers that often hide systemic issues.
  • p99.9 — worst-case; matters for high-volume services.

SLOs should be defined on percentiles, not averages. "99% of requests under 500ms" not "average under 500ms".

Prometheus example:

histogram_quantile(0.99,
  sum(rate(http_request_duration_seconds_bucket[5m])) by (le, route))
Q58 How do you design good alerts?

Answer

  • Alert on symptoms, not causes. Page on "user-facing latency > 1s" not "CPU > 80%". CPU at 80% might be normal; latency degrading is what the user feels.
  • Every page should be actionable. If the responder can't do anything about it, it shouldn't page. Demote to a ticket or dashboard.
  • Severity tiers. Page only on SEV1/SEV2. Tickets for SEV3/SEV4.
  • Include context. Alert payload should have: link to dashboard, link to runbook, recent deploys, ownership.
  • Multi-window, multi-burn-rate alerts (SRE workbook) — alert when burn rate is high over a short window AND moderate over a long window. Reduces false positives while keeping fast detection.
  • Avoid threshold-based-on-vibes. Pick thresholds from SLO math, not "5% seems bad".
  • Quarterly alert review — kill noisy alerts, fix runbooks, tune thresholds.
Q59 What is alert fatigue and how do you fight it?

Answer

Alert fatigue is when responders start ignoring alerts because too many are noise. The result: real alerts get missed.

Counter-measures:

  • Track alert volume per on-call shift. If on-call gets > 2 actionable pages per week, the alerting strategy is broken. Spend engineering time fixing the noisy alerts, not just suffering them.
  • Don't page on anything a runbook can resolve. Automate the runbook or demote to ticket.
  • De-duplicate — one underlying issue should fire one page, not 50 (use grouping, dependency-aware alerting).
  • Symptom-based alerts reduce duplication because they catch many root causes at one symptom.
  • Auto-resolve — alerts should clear when the condition does, not stay open requiring manual ack.
  • Make every page have a postmortem trigger if it's a false positive. Treat noisy alerts as bugs.
Q60 What is structured logging and why does it matter?

Answer

Structured logging emits logs as key-value pairs (typically JSON) rather than free-text strings.

Unstructured: User alice failed to checkout, order=123, code=AUTH_FAIL

Structured:

{"level":"warn","msg":"checkout failed","user":"alice","order_id":123,"error_code":"AUTH_FAIL","trace_id":"abc..."}

Benefits:

  • Searchable by field — find all checkouts for user alice.
  • Aggregatable — count error_code=AUTH_FAIL over time.
  • Joinable with traces and metrics via trace_id.
  • Robust to format drift — adding a field doesn't break parsers.

Best practices: include trace_id and span_id, request_id, user_id (or anonymous ID), service name, version, environment in every log line.

Q61 What is distributed tracing and what problem does it solve?

Answer

In a microservices system, a single user request fans out across many services. When latency or errors happen, you need to know which service caused them. Logs alone don't show causality across services.

Distributed tracing propagates a trace_id through every service that handles a request. Each service emits "spans" (units of work) tagged with that trace_id and its parent span_id. The collector assembles a tree showing where time was spent.

Standards: OpenTelemetry (OTel) is the vendor-neutral standard. SDKs auto-instrument popular libraries (HTTP, DB, queues). Backends: Jaeger, Tempo, Honeycomb, Datadog APM, AWS X-Ray.

Practical use: "Why was checkout slow at 14:23?" → find slow traces → see span tree → discover one DB call took 4s while the rest took 50ms → drill into that query.

Q62 Your logging system is overloaded. What do you do?

Answer

Immediate

  • Identify the source of the spike — usually one service logging in a tight loop or at DEBUG level by accident.
  • Drop or sample at the agent (Fluentd/Vector/Promtail) — keep ERROR/WARN, sample INFO.
  • Block the noisy source's ingestion temporarily.

Long-Term

  • Log levels in production: WARN/ERROR by default, INFO sparingly, DEBUG only on demand.
  • Sample high-volume INFO logs (1 in 100) and keep all errors.
  • Move to structured logging so you can filter cheaply at ingest.
  • Per-service log quotas; the team owning the loud service is responsible for the cost.
  • Trace-based sampling: log everything for a sampled fraction of traces, nothing for the rest.
  • Treat logs as a metric source for high-volume events — instead of logging every request, increment a counter.
Q63 How do you correlate metrics, logs, and traces?

Answer

The connective tissue is identifiers:

  • trace_id in every log line and every metric tag where cardinality allows (e.g., exemplars on histograms).
  • service.name, service.version, deployment.environment consistently across all three.
  • OpenTelemetry semantic conventions standardize tag names so dashboards work across services.

Workflow: See latency spike on a Prometheus dashboard → click an "exemplar" point that links to a sample trace → in the trace, find the slow span → click into the logs filtered by that trace_id.

Modern tools (Datadog, Honeycomb, Grafana stack) automate this navigation. Even without those tools, including trace_id in structured logs gets you most of the way.

9. SRE Concepts: SLA / SLO / SLI / Error Budget / Toil / On-Call

Q64 Explain SLI, SLO, and SLA. How do they relate?

Answer

  • SLI (Service Level Indicator): A measurement. "The fraction of HTTP requests in the last 5 minutes that returned 200 within 500ms." A specific, numeric, quantifiable thing.
  • SLO (Service Level Objective): An internal target on an SLI. "99.9% of requests over a 28-day window should meet the SLI." This is what the engineering team commits to.
  • SLA (Service Level Agreement): A contractual obligation to customers, with penalties (refunds, credits) if missed. SLA is always less strict than SLO — you want a buffer to react before you breach the contract.

Hierarchy: SLI (what we measure) → SLO (what we target) → SLA (what we contractually promise). Practitioners design SLI/SLO; SLA is a business document.

Example:

  • SLI: success rate of POST /checkout
  • SLO: 99.95% over 28 days
  • SLA: 99.9% over a calendar month — refund if breached
Q65 What is an error budget and how do you use it?

Answer

The error budget is the inverse of the SLO: if your SLO is 99.9% over a month, you have a 0.1% error budget — roughly 43 minutes of allowed failure.

How it's used:

  • Risk management policy: if there's budget remaining, ship new features at full speed. If the budget is exhausted, freeze risky deploys and focus on reliability work.
  • Conflict resolution between product and SRE: instead of debating "is this change safe?", ask "do we have budget for it?". The data decides.
  • Investment signal: repeatedly exhausting the budget means the SLO is too tight (negotiate with stakeholders) or reliability work is under-invested.
  • Burn rate alerts: alert when you're burning budget faster than expected. E.g., burning 14× normal rate means a 28-day budget is gone in 2 days — page immediately.

The error budget makes reliability a negotiable engineering trade-off rather than an absolute goal ("never have downtime"), which is the core insight of SRE.

Q66 What is toil and why does it matter?

Answer

Toil is operational work that is:

  • Manual (a human types commands)
  • Repetitive (you do it again next week)
  • Automatable (a machine could do it)
  • Tactical, not strategic (no lasting value)
  • Devoid of enduring value (the service is no better after than before)
  • Linear with service growth (more users = more of this work)

Why it matters: toil is the silent killer of SRE teams. Left unchecked, it grows linearly with the service while engineers want to do project work. Google's guideline: SRE teams should spend ≤ 50% of time on toil. If above, escalate and invest in automation.

Examples: Manual capacity expansion, certificate rotation by hand, on-call paging for the same issue weekly, restarting a service every Monday.

Not toil: Designing systems, writing automation, postmortems, code reviews, on-call for genuinely novel issues.

Q67 What makes a good runbook?

Answer

  • One per alert. The alert payload includes a direct link to the runbook for that specific alert.
  • Starts with "verify" — was the alert real? What signals confirm?
  • Triage section — who's affected, how to assess scope.
  • Mitigation steps — copy-paste-able commands. Mitigation comes before diagnosis.
  • Diagnosis section — common causes and how to check each.
  • Escalation — who to wake up if the on-call can't resolve, with phone numbers.
  • Tested. Run the runbook in a game day periodically. Stale runbooks are worse than no runbooks because they mislead.
  • Updated after every incident. Anything you wished was in there → add it.

Anti-patterns: Wall of text, no commands, references to non-existent dashboards, last updated 3 years ago.

Q68 What does a healthy on-call rotation look like?

Answer

  • Predictable schedule — minimum 6 engineers in rotation so each shift is ≤ 1 week every 6 weeks. Smaller rotations burn people out.
  • Coverage with handoff — explicit handoff at shift boundary including open incidents, recent alerts, ongoing changes.
  • Low page volume — ≤ 2 actionable pages per shift. If higher, the alerting strategy is broken.
  • Compensation — money or time off for being on call. Treat it as work, not "part of the job".
  • Backup / secondary — if primary doesn't ack in N minutes, escalate to secondary.
  • Runbooks for every alert.
  • Postmortems for every page at minimum at the metric level — was this page actionable? If not, fix it.
  • Follow-the-sun for global teams to avoid night pages where possible.
  • Engineers can opt out in life situations (new parent, illness) without career penalty.
Q69 What's the difference between MTTR, MTBF, MTTD, and MTTA?

Answer

  • MTTD (Mean Time To Detect): Time from incident start until your monitoring noticed.
  • MTTA (Mean Time To Acknowledge): Time from page until a human acknowledges they're working on it.
  • MTTR (Mean Time To Recover or Repair or Resolve — definitions vary): Time from incident start until service is restored. Sometimes split as MTTM (mitigate) vs MTTR (full repair).
  • MTBF (Mean Time Between Failures): Average healthy period between incidents.

SRE focus: Detection (MTTD) and recovery (MTTR) are usually more tractable than preventing failures (MTBF). Modern complex systems will fail; design for fast recovery, not just fewer failures.

Caveat: "Mean" can hide bad tails. Reporting p95 MTTR alongside the mean is more honest.

Q70 Should you have a 100% uptime SLO?

Answer

No. 100% is the wrong target. Reasons:

  • It's impossible. Customer ISPs go down, DNS resolves wrong, networks blip. Failures outside your control happen.
  • It's economically wasteful. Going from 99.9% to 99.99% may cost 10× more in infrastructure and engineering. Customers may not value the difference.
  • It eliminates the error budget, which means no allowance for shipping anything risky — you stop being able to deliver features.
  • Even client SDKs and the network between you and the user have lower availability than 100%. Promising more than that is incoherent.

The right SLO depends on the business. A bank's auth might be 99.99%. An internal analytics tool might be 99%. Determine by asking customers what they actually need and what they're willing to pay for.

Q71 What is "chaos engineering" and is it worth doing?

Answer

Chaos engineering is the practice of deliberately injecting failures into a production-like system to verify that the system tolerates them (and to find places where it doesn't). Originated at Netflix with Chaos Monkey.

Common experiments:

  • Kill a random pod / instance.
  • Inject network latency or packet loss between services.
  • Block a dependency for 5 minutes.
  • Fail over a database.
  • Saturate CPU or fill disk on a node.

Worth doing if: you have an SLO, observability, and graceful-degradation patterns. Without those, you'll just cause incidents. Start in staging, then non-business-hours production, then steady-state.

Tools: Chaos Monkey, Gremlin, Litmus, AWS Fault Injection Simulator.

10. Scenario-Based Troubleshooting

Q72 Scenario: The login service degraded 3 minutes after a deploy. Latency p99 went from 200ms to 8s. Walk me through your response.

Step 1 — Stabilize

  1. Initiate rollback immediately. The temporal correlation with deploy is overwhelming.
  2. Verify rollback completes and metrics return to normal.
  3. Update internal channel: "Rolled back to v1.42. Latency recovering. Investigating cause."

Step 2 — Investigate (post-mitigation)

  1. Pull the deploy diff (v1.43 vs v1.42).
  2. Check traces from the affected period — which span got slow? Most likely candidates: new DB call, new external HTTP call, new sync I/O, lock contention.
  3. Look at the database — slow query log entries, connection pool saturation, lock waits.
  4. Look at GC / thread pool metrics — sudden change in pool exhaustion or GC pause times often points to a new code path.
  5. Reproduce in staging with load to confirm.

Step 3 — Prevent

  • Add a load test to staging that would have caught the regression.
  • Canary the next deploy at 5% traffic for 15 minutes with auto-rollback on latency breach.
  • Action item: every PR that adds a network or DB call must have a perf note in the PR description.
Q73 Scenario: Your Kubernetes cluster's etcd is reporting high latency and master API is intermittently failing. What now?

Answer

etcd is the brain of Kubernetes. Latency on etcd cascades to every API operation.

Investigation

  1. Disk IOPS — etcd is fsync-intensive. Slow disk is the #1 cause. Use NVMe / Provisioned IOPS SSD; never magnetic.
  2. Disk space — etcd has a default 2GB quota; if near full, etcd refuses writes. Compact and defragment.
  3. Network — etcd cluster members must have low-latency interconnects. Cross-AZ etcd works but is sensitive.
  4. API request volume — a misbehaving controller doing tight watch/list loops can DoS etcd. Find the noisy client in audit logs.
  5. Object count — too many objects (especially Events, ConfigMaps from CI noise) bloats etcd.

Mitigation

  • Compact: etcdctl compact <rev> and defrag: etcdctl defrag.
  • Stop or rate-limit the noisy controller.
  • Delete stale Events / unused namespaces.
  • If a single etcd member is bad, remove and rejoin.

Prevention

  • Run etcd on dedicated nodes with fast local SSDs.
  • Alert on etcd disk space, leader changes, and fsync latency.
  • Run managed Kubernetes (EKS/GKE/AKS) to delegate etcd ops if you can.
Q74 Scenario: The customer-facing API works but the admin dashboard times out. They share the same backend. Where do you look?

Answer

"Same backend, only one path broken" is a useful constraint. Things that could be different:

  • Different endpoints — the admin endpoint runs a heavy query (full-table scan, complex join) the customer endpoints don't. Check the admin endpoint's DB query plan.
  • Different auth path — admin uses SSO/SAML which is timing out at the identity provider.
  • Different load balancer or routing — admin behind a different LB/proxy/firewall rule.
  • Different rate limits — admin throttled lower than customer API.
  • Admin connects to a primary DB while customer API hits replicas; primary is overloaded.
  • Different timeouts — admin LB has a short timeout that's killing long but valid queries.

Step one: identify which downstream operation times out (a span in a trace or the slow log).

Q75 Scenario: Your application has a memory leak. How would you find it in production without restarting?

Answer

Approach

  1. Profile the live process.
    • JVM: jcmd <pid> GC.heap_dump /tmp/heap.hprof, then analyze with Eclipse MAT.
    • Go: hit /debug/pprof/heap (pprof endpoint), go tool pprof.
    • Python: py-spy dump --pid <pid>, tracemalloc, memray.
    • Node.js: --inspect flag + Chrome DevTools heap snapshot.
  2. Compare snapshots over time — take heap dumps at T+0, T+30min, T+1h. Objects with growing retained size are the suspects.
  3. Continuous profiling (Pyroscope, Parca, Datadog Continuous Profiler) gives you the trend without dumping.
  4. Check application patterns: static caches without eviction, unbounded queues, listeners not deregistered, connection leaks (DB, HTTP).

Mitigation

  • Rolling restart while you fix.
  • Set memory limits + restart policy so OOM doesn't take down the cluster.
  • If a specific endpoint is the leaker, route around it via feature flag.
Q76 Scenario: CloudWatch alarms show CPU is fine but customers report slowness. Why might that be?

Answer

Low CPU + slow responses = the bottleneck is something other than compute. Candidates:

  • Network/IO bound — high disk read latency, slow downstream API calls, network packet loss.
  • Lock contention — threads waiting on mutexes, DB row locks. CPU appears idle because threads are blocked, not running.
  • Thread pool exhaustion — all threads are waiting on slow I/O; no spare workers to handle new requests. CPU is idle but queue is full.
  • Garbage collection — long pause times block requests; cumulative CPU may not reflect spike.
  • Burstable instance throttling (T-series) — CPU credits exhausted. CloudWatch shows CPUSurplusCreditBalance / CPUCreditBalance specifically.
  • Connection limits — DB connection pool maxed; new requests queue.
  • Single-threaded bottleneck — node.js / Python with one event loop can saturate even when the machine has 16 idle cores.

Look at RED metrics (Rate, Errors, Duration) at the application layer rather than only at host metrics.

Q77 Scenario: A scheduled batch job has been failing silently for a week. Customer-impacting data is stale. How do you handle?

Answer

Immediate

  1. Quantify the impact — what data is stale, which customers are affected, how stale.
  2. Manually trigger the job to recover current state.
  3. Communicate to affected customers/internal users — even if not externally visible, transparency builds trust.

Investigation

  1. Why did it fail? Logs, error messages, was there a recent change?
  2. Why didn't we notice? This is the more important question. The job had no alert on "didn't complete" or "didn't produce output" or "result count dropped to zero".

Prevention

  • Liveness for batch jobs: alert if a job hasn't run successfully in N expected periods (a "dead man's switch").
  • Output validation: alert if the output is empty, smaller than expected, or stale (e.g., timestamp > N hours old).
  • Pipeline-level SLO: data freshness as an SLI.
  • Use a workflow orchestrator (Airflow, Prefect, Dagster) that surfaces failures explicitly rather than cron-and-pray.
Q78 Scenario: A production database is at 95% storage with auto-scaling disabled. It will fill within 4 hours. What do you do, in order?

Answer

Time-critical. Buy time, then fix.

Buy time (in parallel)

  1. Expand storage now — RDS modify-db-instance with new size, or PostgreSQL/MySQL on EBS resize. AWS storage scale-up is online but takes 10–30 min and can't be repeated for 6 hours.
  2. Stop ingestion of low-value data — if you have heavy logging into the DB (anti-pattern but common), pause it.
  3. Identify and delete free wins — old soft-deleted rows, expired sessions, large unused tables (look at pg_total_relation_size / information_schema). DROP/TRUNCATE if safe.
  4. VACUUM FULL with caution — locks tables. Better: VACUUM (no FULL) and pg_repack for online reclamation.
  5. WAL/binlog cleanup — if WAL retention is enabling replicas you don't need, reduce. Be careful — don't break replication you do need.

After

  • Enable storage auto-scaling immediately.
  • Add alert at 70% / 80% / 90%.
  • Define data retention policy and automate purges.
  • Audit table growth rates; the biggest grower needs a partitioning or archival strategy.
Q79 Scenario: A new microservice you launched is causing the message queue to back up. Consumers can't keep up. How do you respond?

Answer

Immediate

  • Scale consumers horizontally — more replicas, more partition consumers (Kafka) / threads.
  • Identify the bottleneck — is the consumer slow due to a downstream (DB, external API)? Then more consumers won't help; they'll DOS the downstream.
  • Drop or DLQ low-priority messages if the queue supports filtering / multiple consumer groups.
  • Pause producers if possible (rare luxury) so consumers can catch up.

Diagnose

  • Per-message processing time — has it increased? GC pauses? Slower downstream?
  • Message size grew unexpectedly?
  • Producer rate spiked from a specific source?
  • Consumer lag per partition (Kafka) — is it one slow consumer or all?

Long-Term

  • Autoscale consumers based on lag (KEDA for Kubernetes).
  • SLO on lag — alert before users notice.
  • Bound queue depth at producer; back-pressure rather than infinite buffering.
  • Capacity-test with realistic peak burst rates.
Q80 Scenario: An expired TLS certificate just took down your service. Walk me through immediate response and prevention.

Answer

Immediate

  • Renew the certificate from the CA (Let's Encrypt, ACM, internal CA).
  • Replace the certificate on every load balancer / ingress / target that uses it.
  • Validate with openssl s_client -connect host:443 -servername host.

Prevention (this should never happen again)

  • Automate renewal — cert-manager in Kubernetes, ACM for AWS LB, certbot for traditional servers. Manual renewal is a recipe for the next outage.
  • Inventory certificates — every cert in use, with expiry date, owner, renewal mechanism.
  • Alert at 30, 14, 7 days before expiry — multiple thresholds, multiple owners.
  • Wildcard or SAN consolidation — fewer certs = fewer chances to forget one.
  • Game day: simulate a near-expiry to verify renewal automation works.

Note: this is the single most preventable outage type in our industry. If your org has had one, an unrenewed cert was almost certainly involved in a major outage at some point.

Q81 Scenario: A vendor's API your service depends on went down. Customers see your site as broken. What do you do?

Answer

Immediate

  • Verify it's the vendor — check their status page; reproduce the failure; check if it's specifically network-pathed to them.
  • Activate graceful degradation — if you've designed it, flip the flag that disables that feature with a clear UI message ("This feature is temporarily unavailable").
  • Serve cached responses if applicable; better stale than nothing.
  • Communicate to customers — be honest about the dependency. "An upstream provider is experiencing an outage; we are monitoring."

Long-Term

  • Vendor SLA awareness — your SLO must be lower than each vendor's SLO unless you have redundancy.
  • Redundancy — multi-vendor for critical paths (e.g., two payment providers, two SMS providers, two DNS providers).
  • Caching for tolerable staleness.
  • Circuit breakers so vendor outage doesn't cascade into your service.
  • Vendor incident playbook — pre-defined: when status page = down for >N minutes, do X.

11. Senior-Level Reasoning & Outage Decision-Making

Q82 How do you balance moving fast with reliability?

Answer

This is the central tension of SRE. The right answer isn't "more reliability" or "more speed" — it's making the trade-off explicit using:

  • Error budgets: if you're meeting your SLO, ship fast. If you're burning budget, slow down. The number decides, not opinions.
  • Differentiated risk: a UI tweak can ship aggressively; a payment flow change needs more rigor. The pipeline can enforce stricter gates per component.
  • Risk-reducing techniques over risk-avoidance: canary, feature flags, blue/green, dark launches. These let you ship and still be safe.
  • Investment in automation: the reason orgs slow down isn't usually that they're "careful"; it's that they lack tooling. Invest in CI, observability, fast rollback, and you can go fast safely.

The bad answer is "we don't ship to production after 3pm Friday." That's a process workaround; it doesn't solve the underlying brittleness.

Q83 During an outage, when do you escalate? When do you not?

Answer

Escalate when:

  • You've been working on it for the threshold time (15–30 min) without progress and you're not sure of next steps.
  • Impact is growing despite your actions.
  • You don't have access/permissions you need.
  • Resolution requires a decision above your authority (e.g., declaring a SEV1, communicating to enterprise customers, taking a destructive action like failover).
  • You're getting tired / making mistakes / over your head.

Do NOT escalate when:

  • You just want company. Escalations should add specific value.
  • You haven't tried the runbook.
  • You're embarrassed — fear of looking bad is the #1 reason engineers delay escalation, and the cost to the company is high.

Healthy escalation culture: escalating early is praised. Senior staff appreciate being looped in on something that turns out fine more than being surprised by a SEV1 they could have helped on at hour 0.

Q84 The team is debating whether to revert vs. fix forward during an outage. How do you decide as the IC?

Answer

As Incident Commander, you don't take sides — you make a decision and own it. The criteria:

  • Reversibility: Is the previous state safely reachable? If yes, revert defaults to safer.
  • Confidence in the fix: Is the "fix" being proposed actually understood, or is it a hypothesis? Production is not the place to test theories.
  • Time pressure: Customer impact severity dictates urgency. If millions of dollars per minute, the revert that takes 5 minutes beats the fix that takes 30.
  • Cost of revert: Sometimes reverting loses data (a migration ran), forces customers to re-do work, or has unrelated risk. Then fix-forward may be justified.

Decision framework: "We will revert in N minutes unless we have a confirmed fix that's been peer-reviewed." Set a hard timer. Don't let the debate run forever.

Document the decision and rationale in the incident channel so it's clear who decided what when.

Q85 A junior engineer caused a production incident. How do you handle it?

Answer

The first principle: the system let it happen. A junior engineer should not have the power to take down production with a single command without a guardrail. If they did, that's the system's fault.

What I would do:

  1. Resolve the incident first. The engineer might be panicking; assign them a task that helps (capturing logs, running a benign command) so they're useful and not paralyzed.
  2. In the postmortem, reinforce that the focus is on systems, not blame. Ask the engineer to write the postmortem if they're up for it — this is a fantastic learning moment.
  3. Action items: add the guardrail. Two-person approval, paved-path tooling, dry-run mode, automated diff preview before apply.
  4. Privately, talk to the engineer afterward. Reassure them. Many engineers' careers are made by the first incident they cause and learn from. Some of the best SREs caused memorable outages early on.

Avoid: shaming, demotion-as-discipline, isolating them. Those signals teach the org to hide mistakes.

Q86 Your team is repeatedly missing the SLO. What's your plan?

Answer

  1. Diagnose the pattern. Is it one incident type recurring? Many different one-off issues? Slow burn from background errors?
  2. Look at top error categories. Pareto: usually 80% of budget burn is from 20% of causes. Fix those first.
  3. If the SLO is wrong (e.g., set without data and unrealistic), negotiate. Either raise the SLI's standard or lower the SLO target. A perpetually-missed SLO is useless.
  4. Pause feature work per the error budget policy. This is uncomfortable, but it's the contract. If product leadership wants to ship despite budget exhaustion, they own the reliability risk — that's an executive decision, not the team's.
  5. Invest in the systemic causes. Often missing SLO points to: insufficient test coverage in CI, no canary, no rollback automation, brittle dependencies. Each is an engineering project.
  6. Track action item completion from past postmortems. Often the same items keep being filed and not done — that's a process failure, not a reliability one.
Q87 A stakeholder is asking for 99.999% availability. How do you respond?

Answer

Don't just say "no". Take the request seriously and walk them through the math.

  • 99.999% = 5 minutes downtime per year. That's less than a single deploy rollout.
  • What's the business need behind it? Sometimes the stakeholder picked the number aspirationally. Sometimes there's a contractual or competitive driver. Understand which.
  • Show the cost. Multi-region active-active, redundant dependencies, formal verification of deploys, dedicated SRE staffing, error budget policies, vendor diversity — likely 5–10× the cost of 99.9%.
  • Show the ceiling. Your dependencies (cloud provider, DNS, payment vendors) may not be 99.999%. You can't be more reliable than your dependency floor unless you have redundancy across providers.
  • Propose alternatives: "Could we commit to 99.95% with rapid recovery on any incident?" or "Could we tier — checkout is 99.99%, analytics is 99.9%?"

The job of a senior engineer in this conversation is to translate business desire into engineering reality, not to capitulate or refuse outright.

Q88 How do you build reliability culture in an engineering organization?

Answer

  • Make reliability data visible. SLO dashboards on every team's wall (literal or virtual). Make it normal to look at them.
  • Blameless postmortems as a standing practice. Share write-ups across the org so other teams learn.
  • Error budget policy — automatic, not a suggestion. When budget is gone, features wait.
  • Rotate developers through on-call for the systems they own. They feel the pain of bad code; they prioritize differently.
  • Celebrate reliability work publicly — when someone reduces toil by 80% or kills a noisy alert, recognize it like a feature ship.
  • Hire SREs as partners, not janitors. SRE consults on design, not just cleanup.
  • Senior leaders own SLOs. If only the SRE team cares, the culture won't shift. CEOs and VPs need to know SLO health.
  • Make doing the right thing easy. Paved paths for deploys, monitoring scaffolding, secret rotation, etc. The default should be safe.
Q89 What's the biggest mistake engineers make during incidents?

Answer

Several common ones, all rooted in cognitive overload under stress:

  • Tunnel vision on the first hypothesis. You believe the issue is X, you investigate X for 20 minutes, you ignore signals pointing to Y.
  • Not stopping the bleeding first. Investigating before mitigating; debugging at length while customers suffer.
  • Multiple uncoordinated changes. Five people typing kubectl commands in parallel makes the outage worse.
  • Not communicating. Heads-down debugging while stakeholders are in the dark.
  • Working alone. Refusing to escalate or pair, often out of pride or fear.
  • Skipping rest. Hour 4 of a 6-hour incident: the responder is exhausted, decision quality drops, mistakes compound. Hand off.
  • Not preserving evidence — restarting the broken service before grabbing a heap dump, killing the bad pod before getting logs.

The discipline is process, not cleverness. Senior engineers have learned the process. They are not necessarily smarter; they are calmer and more methodical.

Q90 What's the one thing you wish more people understood about production systems?

Answer

Different people will give different answers; here are some senior takes that resonate:

  • Failure is normal. Complex systems exist in a permanent state of partial degradation. Successful operations is the management of unfolding failure, not its prevention.
  • Most outages are caused by changes — your changes. Not hardware failures, not attacks, not load. Deploys, config edits, manual fixes. If you want fewer incidents, reduce risky changes — or get much better at making changes safely.
  • The system that's running in production is not what's described in the documentation. It's an emergent thing shaped by years of patches, workarounds, and forgotten decisions. Respect that history.
  • Reliability is a feature. Engineers often see it as a tax on feature work. But unreliable products lose customers no matter how cool the features are. Reliability work is product work.
  • The first 5 minutes of an incident set the tone for the next hour. Don't skip the basics: incident channel, IC role, rollback as default, communicate.
  • Your job is not to prevent all incidents. It's to make sure the ones that happen are short, contained, and learned from.
