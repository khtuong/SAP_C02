00How to use this cheatsheet

Three passes work best: (1) skim the Keyword Decision Matrix, (2) study the six domains in order, (3) drill the Trap Answers section the night before the exam.

1Read scenario for keywords

Every DOP-C02 question hides 2–3 keyword anchors (e.g. "least operational overhead", "blue/green", "drift", "automatic remediation"). Spot them first — they collapse 4 options to 1–2.

2Eliminate trap answers

~50% of distractors fail one of: manual step deprecated service wrong scope missing IAM. Strike them first.

3Pick the most-managed option

If two answers are equivalent, the one with more managed AWS services (Lambda over EC2, Step Functions over cron) is usually correct — DevOps Pro favors automation.

⚡ Decision heuristic — use this on every question

Ask in order: ① Is it least-ops/managed? ② Is it automated end-to-end? ③ Is it the smallest blast radius? ④ Does it use the purpose-built AWS service for the keyword? — When two answers tie, pick the one that uses Systems Manager / EventBridge / Step Functions instead of cron, SSH or custom scripts.

D1 · 22%SDLC Automation

CI/CD pipelines, deployment strategies, automated testing, artifact management, and integrating quality gates. The largest domain — master this first.

CPCodePipeline

Orchestrator. Stages → Actions. Cross-region/cross-account supported via S3 + KMS.

  • Manual approval action for prod gates.
  • EventBridge is the only way to trigger CodePipeline on a schedule (no native cron).
  • Cross-account: KMS key + bucket policy + role in target account.
CI/CDManaged

CBCodeBuild

Build + test runner. Define build steps in buildspec.yml.

  • Use reports phase for JUnit/Cucumber test reports.
  • Use local cache (Docker layer / source) for speed.
  • VPC mode required to reach private resources (RDS, internal endpoints).
BuildTest

CDCodeDeploy

Deployment engine for EC2 / on-prem / ECS / Lambda. Choose the right strategy.

  • In-place (EC2): rolling, half-at-a-time, one-at-a-time, all-at-once.
  • Blue/Green: new fleet → swap via ELB. Required for Lambda & ECS.
  • Hooks: BeforeInstall, AfterInstall, ApplicationStart, ValidateService.
  • AppSpec lives in repo root.
DeployBlue/Green

CCCodeCommit

Managed Git. IAM-controlled. Trigger pipelines via EventBridge / CloudWatch Events on push.

  • Approval rule templates enforce reviewers on PRs.
  • Replicate cross-region via EventBridge → CodeBuild → push to second repo.

CACodeArtifact

Private package manager for npm/Maven/PyPI/NuGet. Use as upstream proxy to public repos to inspect/control dependencies.

  • Domain → Repository → Packages. KMS-encrypted by default.
  • Replace S3-as-artifact-store for code dependencies.

GCodeGuru

Reviewer: automated code reviews on PRs. Profiler: production performance profiling.

  • Reviewer integrates with CodeCommit, GitHub, Bitbucket.
  • If question says "find security issues in code" + low-effort → CodeGuru Reviewer.

🟢 High-yield CI/CD facts

  • Cross-account deploy: use CodePipeline in account A with an S3 artifact bucket + KMS CMK shared via key policy + cross-account IAM role in account B. Never use access keys.
  • Approval before prod: insert Manual approval action — wire SNS notification for reviewers.
  • Trigger on schedule: CodePipeline has no schedule → use EventBridge rule on cron expression → StartPipelineExecution.
  • Quality gate: CodeBuild test step → if failure, pipeline stops. Reports go to codebuild-reports dashboard.
  • Artifact security: KMS CMK + bucket SSE-KMS + bucket policy denying s3:PutObject without x-amz-server-side-encryption.

🔴 Trap answers in SDLC questions

  • Any answer using Jenkins on EC2 when the question says "least operational overhead" — wrong, prefer CodeBuild.
  • Using CodeCommit triggers via SNS → Lambda for pipeline starts — outdated. Modern answer uses EventBridge.
  • Storing secrets in buildspec.yml — always wrong. Use Secrets Manager or SSM Parameter Store via env_variables/parameter-store/secrets-manager mapping.
  • Manual CodeDeploy hooks doing SSH installs — DevOps Pro hates this. Use AppSpec + CodeDeploy Agent.

D2 · 17%Configuration Management & Infrastructure as Code

CloudFormation patterns, Systems Manager, Beanstalk, OpsWorks, Service Catalog. CloudFormation appears on nearly every test — internalize the patterns.

CFCloudFormation

  • StackSets = deploy stacks across multiple accounts/regions. Use with AWS Organizations for trust.
  • Drift detection = find manual changes vs template. Schedule with EventBridge + Lambda.
  • Change Sets = preview before apply (production safety).
  • Helpers: cfn-init, cfn-signal, cfn-hup — instance bootstrap & signal back.
  • DeletionPolicy: Retain / Snapshot for stateful resources.
  • UpdateReplacePolicy protects on replacement updates.
  • Stack policies = JSON deny rules that protect specific resources from updates.

SMSystems Manager (SSM)

  • Patch Manager + Maintenance Windows = patch fleets on schedule. Use patch baselines per OS.
  • Run Command = ad-hoc commands across fleet (no SSH).
  • State Manager = enforce desired configuration continuously.
  • Session Manager = SSH-free shell access; logs to S3/CloudWatch.
  • Parameter Store = config/secrets, free tier; SecureString uses KMS.
  • Automation Documents = remediation runbooks (great with Config rules).
  • Inventory = collect software & metadata; query via Resource Data Sync → S3 → Athena.

EBElastic Beanstalk

  • Deployment policies: All-at-once / Rolling / Rolling-with-additional-batch / Immutable / Blue-Green.
  • .ebextensions for env config (option_settings, files, packages, container_commands).
  • Saved configurations reproducible across envs.
  • Worker tier + SQS for background jobs.

OWOpsWorks

Chef/Puppet config management. Mostly legacy on the exam — answer is usually not OpsWorks unless explicitly required. Prefer Systems Manager instead.

SCService Catalog

Curated portfolios of approved CloudFormation products. Used for self-service provisioning with guardrails.

  • Constraints: launch role, template, tag-update.
  • Pair with Organizations to share portfolios across accounts.

ACAppConfig

Feature flags & runtime config with safe deployment (linear, canary) + validators (JSON Schema or Lambda) + alarms-based automatic rollback.

Best answer when question says "change config without redeploy" or "feature flags".

🔴 IaC trap answers

  • "SSH to each EC2 and run yum update" → wrong. Always SSM Patch Manager.
  • "Custom Lambda to detect drift" → wrong. CloudFormation drift detection is purpose-built.

D3 · 15%Resilient Cloud Solutions

High availability, disaster recovery, scaling, multi-region. Memorize the four DR patterns by RTO/RPO.

DRThe 4 DR strategies

ASAuto Scaling tactics

  • Lifecycle hooks = pause Pending:Wait / Terminating:Wait to drain or capture logs.
  • Warm pools = pre-initialized instances for fast scale-out.
  • Predictive scaling = ML on historical metrics — for predictable diurnal traffic.
  • Termination policies = OldestInstance, OldestLaunchConfiguration, ClosestToNextInstanceHour.
  • Mixed instances policy = combine On-Demand + Spot for cost.
  • Use ASG instance refresh for rolling AMI updates without CodeDeploy.

R53Route 53 routing

  • Failover (primary/secondary) — health-check driven.
  • Latency-based — global low-latency.
  • Weighted — gradual cutover / A/B testing.
  • Geolocation / Geoproximity — compliance routing.
  • ARC (Application Recovery Controller) — for advanced multi-region failover.

DBStateful HA

  • RDS Multi-AZ = sync replica, automatic failover, same region. Not for read scaling.
  • Aurora Global DB = <1s replica, <1min failover, cross-region.
  • DynamoDB Global Tables = active-active multi-region with last-writer-wins.
  • S3 Cross-Region Replication (CRR) = replicate buckets to another region; SRR = same region (compliance/log aggregation).
  • AWS Backup = central backup with policies + cross-account/region copy.
  • EBS DLM = scheduled snapshots + retention.

🔴 Resilience traps

  • "RDS Read Replica" as DR answer — partial credit only. Cross-region read replica can be promoted, but Aurora Global DB is the modern Pro-level answer.
  • Multi-AZ ≠ Multi-Region. Always check if the question wants region-level failover.
  • "Lambda function to copy snapshots nightly" — wrong. Use AWS Backup or DLM.

D4 · 15%Monitoring & Logging

CloudWatch, CloudTrail, X-Ray, EventBridge. Almost every question includes some monitoring component — learn the operators.

CWCloudWatch Logs

  • Metric Filter = parse logs → emit metric (e.g. count of ERROR lines).
  • Subscription Filter = stream logs in real-time to Kinesis / Firehose / Lambda / OpenSearch.
  • Logs Insights = ad-hoc SQL-like query for investigation. Not for real-time alarms.
  • Cross-account aggregation = subscription filter to Kinesis Data Stream in central account.
  • Anomaly detection on metrics for dynamic thresholds.

CTCloudTrail

  • Management events = API calls (default ON).
  • Data events = S3 object-level, Lambda invoke (must opt-in, costly).
  • Insights events = anomalous activity.
  • Send to Organizations trail for multi-account. Always validate log file integrity (digest).
  • Forward to CloudWatch Logs for alarming on API patterns.

XRX-Ray

  • Distributed tracing across services. Use sampling rules to control cost.
  • Active integration: API GW, ALB, Lambda, ECS, EC2 daemon, App Mesh.
  • Detect bottlenecks / errors across microservices in the service map.

EBEventBridge

  • Event bus + rules. Default bus for AWS events; custom bus for app events; partner bus for SaaS.
  • Schemas + registries for typed events.
  • Cross-account via target rules or bus policies.
  • Replaces CloudWatch Events. Triggers Lambda, Step Functions, ECS task, SSM Automation, CodeBuild/Pipeline, etc.

CNContainer Insights

ECS / EKS metrics + logs. Default answer when question mentions container observability.

CACloudWatch Alarms

  • States: OK / ALARM / INSUFFICIENT_DATA.
  • Composite alarms reduce noise — combine multiple alarms with AND/OR.
  • Alarm action → SNS, EC2 action, Auto Scaling, SSM OpsItem.

Log pipeline pattern — memorize this

Centralized multi-account logging:
  1. Each account writes to its own CW Log Group.
  2. Apply a Subscription Filter → forwards to Kinesis Data Stream in a central log-archive account.
  3. Kinesis Data Firehose → S3 bucket (Object Lock for immutability).
  4. Athena queries S3 directly. OpenSearch optional for full-text search.

Pick this over "ship logs via Lambda" or "use SNS topic to fan out" — the subscription filter is the purpose-built way.

D5 · 14%Incident & Event Response

Auto-remediation, notifications, AWS Health, runbooks. The pattern is always: Event → Rule → Action.

AHAWS Health Dashboard

Personalized service events (PHD). Use the Health API + EventBridge to react to scheduled maintenance / impaired services / quota issues automatically.

  • Forward to a central account via Organizations view.
  • EventBridge rule on aws.health → Lambda / SSM Automation.

SNSNS

Pub/sub fan-out. Multiple subscribers per topic (Lambda, SQS, email, HTTPS).

  • Use FIFO for ordered delivery + dedup.
  • Subscription filter policies to route by attribute.

SQSQS

Buffer/decouple. Visibility timeout, DLQ for poison messages.

  • Standard = at-least-once, best-effort ordering.
  • FIFO = exactly-once, ordered.

SFStep Functions

Orchestrate multi-step runbooks (e.g., "isolate instance → snapshot → notify → ticket").

  • Standard for long-running; Express for high-volume/short.
  • Use over chained Lambdas — better observability + retry/catch.

SASSM Automation

Pre-built runbooks (AWS-*) and custom YAML/JSON docs. Excellent for Config remediation, patching, and Health-event reactions.

CHAWS Chatbot

Send CloudWatch / SNS / EventBridge notifications to Slack/MS Teams; run safe commands from chat (e.g. start runbook).

  • Email/SMS to humans → SNS Topic.
  • Slack/Teams → SNS → AWS Chatbot.

D6 · 17%Security & Compliance

IAM, KMS, Secrets Manager, AWS Config, GuardDuty, Inspector, Macie, Organizations, Security Hub. Pro exam pushes hard on multi-account governance.

IAMIAM patterns

  • Roles > users for workloads; never long-lived access keys on EC2.
  • Permission boundaries = max permissions for an identity.
  • SCPs (Organizations) = boundaries at account level. Deny by default at OU.
  • IAM Identity Center (SSO) = central federation for human access.
  • IAM Access Analyzer = surface external access + unused access.
  • ABAC using tags for scalable permissioning.

KMSKMS

  • Customer-managed CMK gives key policy + audit + rotation control.
  • Annual rotation (CMK) — automatic for AWS-managed; opt-in for CMK.
  • Key grants for temporary delegation.
  • Multi-Region keys for cross-region encrypted resources (replicate ciphertext).

CFGAWS Config

  • Config rules (managed or custom Lambda/Guard) — evaluate resource state.
  • Auto-remediation via SSM Automation document.
  • Conformance packs = bundles of rules + remediations (deploy via StackSets).
  • Aggregator = multi-account/region view.

SHSecurity Hub

Aggregates findings from GuardDuty, Inspector, Macie, IAM AA, Firewall Manager, 3rd-party. Runs CIS / AWS FSBP / PCI DSS standards.

  • Findings in ASFF format → EventBridge → SOAR.
  • Cross-account via delegated administrator + Organizations.

GDGuardDuty

Threat detection on CloudTrail, VPC Flow Logs, DNS, S3, EKS audit logs, RDS login activity. ML-based.

INInspector v2

Vulnerability scanning for EC2, ECR images, Lambda. Continuous. Integrates with Security Hub.

MAMacie

Discover & classify sensitive data (PII, PHI) in S3. Findings → Security Hub / EventBridge.

SMSecrets Manager

  • Automatic rotation via Lambda (built-in for RDS, Redshift, DocumentDB).
  • Cross-account via resource policy.
  • VPC endpoint for private fetch.

OROrganizations

  • SCPs enforce guardrails (deny iam:CreateAccessKey, deny non-approved regions, etc.).
  • Delegated administrator for security/audit accounts.
  • Control Tower = blueprint multi-account landing zone.

★Tips, Traps & Exam-Day Strategy

🧠 Top 10 elimination rules

  1. Any answer with SSH / manual / Bastion → likely wrong. Use SSM Session Manager.
  2. Any answer with access keys for workloads → wrong. Use IAM roles.
  3. Any answer with cron on EC2 / Jenkins when a managed service exists → wrong.
  4. Any answer that copies snapshots with Lambda → AWS Backup / DLM is the right one.
  5. Any answer that builds custom drift detection → CloudFormation drift exists.
  6. If question says "least overhead" or "most operationally efficient" → managed service wins.
  7. If question says "scale to thousands of accounts" → Organizations + StackSets.
  8. If two options work, pick the one with fewer custom Lambdas.
  9. Read the LAST sentence first — it's the ask. Then scan the stem for keywords.
  10. For MRQ (pick N): each correct option is independent. Don't force them to fit one story.

⏱️ Time management (180 min, 75 Qs)

  • ~2:20 per question on first pass. Don't get stuck.
  • Use the Flag for Review button generously — return after the first pass.
  • Aim to finish first pass by minute 140; leaves 40 min for flagged + review.
  • If stuck >2 min: pick best guess, flag, move on. Brain often answers in the background.
  • Caffeinate before, hydrate during, bathroom break only if needed (timer doesn't stop).

🚫 Top 10 trap answers to spot

  1. "Schedule a Lambda with rate(1 hour) to check…" — usually replaceable with Config rule / EventBridge.
  2. "Use IAM user with programmatic access" for any service — use roles.
  3. "Install agent X on all servers" — usually SSM has it.
  4. "Hard-code …" anywhere — wrong.
  5. "Use S3 as artifact store across accounts" without KMS — incomplete; KMS CMK + bucket policy required.
  6. "AWS OpsWorks" — almost always a distractor.
  7. "Inspector classic" or "Macie classic" — deprecated.
  8. "Beanstalk for multi-account governance" — wrong scope.
  9. "CloudWatch Events" written instead of EventBridge — usually equivalent, but EventBridge is the modern correct.
  10. "Edit the production stack directly" — never. Always Change Set / CI/CD.

High-yield "must-know" micro-facts

CodeDeploy hook order

ApplicationStop → BeforeInstall → Install → AfterInstall → ApplicationStart → ValidateService. Lambda/ECS use BeforeAllowTraffic / AfterAllowTraffic.

CloudFormation policies

CreationPolicy = wait for cfn-signal. UpdatePolicy = how to update (ASG rolling). DeletionPolicy = Retain / Snapshot / Delete. UpdateReplacePolicy = on replace.

SCP gotcha

SCPs do NOT grant permissions — they only restrict. You still need IAM allow.

S3 encryption defaults

SSE-S3 is default since Jan 2023 on all new buckets. Enforce SSE-KMS via bucket policy condition s3:x-amz-server-side-encryption.

Lambda alias + version

Routing config: {"v2":0.1} for canary. CodeDeploy hooks manipulate alias weight.

ECS rolling vs blue/green

Rolling = native to ECS service. Blue/Green = via CodeDeploy + ALB target groups.

ASG instance refresh

Replaces instances in batches with min healthy %. Use when changing AMI/LT without CodeDeploy.

EventBridge cross-account

Add resource-based policy on the bus in target account allowing source account events:PutEvents.

Aurora vs RDS Multi-AZ

Aurora failover ~30s, RDS Multi-AZ ~60–120s. Aurora replicas are readable; RDS Multi-AZ standby is NOT.

S3 Object Lock

WORM (Compliance / Governance). Required for immutable log archives (often paired with central logging answers).

CodeBuild VPC mode

Required when build needs to reach private RDS/EFS/internal endpoints. Costs more cold starts.

Beanstalk deployment ranking

Speed: All-at-once > Rolling > R-w-additional-batch > Immutable > B/G. Safety is the reverse.

XACross-Account & Multi-Account Patterns Deep Dive

DOP-C02 loves Organizations/multi-account scenarios. Every pattern here recurs.

1 · CI/CD cross-account deploy (3-legged stool)

  • Artifact bucket in CI/CD account encrypted with a customer-managed KMS CMK.
  • KMS key policy grants kms:Decrypt to a role in the target account.
  • S3 bucket policy grants s3:GetObject to the same role.
  • CodePipeline cross-account action role in the target account is assumed by the pipeline.
  • Deploy via CloudFormation StackSet or CodeDeploy in target account.

2 · Multi-account compliance baseline

  • AWS Organizations with OUs (Prod, NonProd, Sandbox).
  • SCPs at OU level for guardrails (no leave-org, no root user, allowed regions).
  • CloudFormation StackSets with service-managed permissions for Config rules, CW Log group baseline, IAM roles.
  • Config Aggregator in audit account collects compliance across accounts/regions.

3 · Centralized logging

  • Org Trail to central S3 with Object Lock + KMS + log file validation.
  • CW Logs subscription filters → Kinesis Data Stream in log-archive account.
  • Firehose → S3 partitioned + Athena queries; OpenSearch optional for full-text search.
  • VPC Flow Logs + Route 53 Resolver query logs → same S3.

4 · Security delegated admin

  • Designate a Security account as delegated administrator.
  • Aggregates GuardDuty / Security Hub / Macie / Inspector v2 / IAM Access Analyzer / Audit Manager / Detective across the Org.
  • Pair with cross-account EventBridge bus to centralize automation.

5 · Central AWS Backup

  • Backup policies managed at Org root → applied to OUs.
  • Vault in central account receives cross-account copies.
  • KMS keys per region + cross-account grants for restore.

6 · Network/Resource sharing

  • AWS RAM: share Transit Gateway / VPC subnets / License Manager / Resolver rules.
  • VPC PrivateLink for cross-account service consumption without peering.
  • Route 53 Resolver rules shared via RAM for hybrid DNS.

7 · ECR image sharing

  • ECR repository policy grants pull to other accounts.
  • Cross-region replication for DR; cross-account replication for multi-account fleets.
  • Scan-on-push with Inspector v2 in the source account; results visible centrally via Security Hub.

8 · Service Catalog hub-and-spoke

  • Portfolio created in hub account, shared with spoke accounts or OUs.
  • Launch constraints use a launch role to provision with elevated permissions.
  • Spoke users get curated products without needing infra permissions.

🎭Trap Phrases Decoder — words that signal the WRONG answer

If an answer choice contains these phrases, treat it as suspicious by default. Eliminate it unless the question explicitly requires it.

🚩 "SSH into the instances" / "Bastion host"
Almost always wrong. → SSM Session Manager (no inbound SSH, IAM-audited, S3/CW logs of sessions).
🚩 "Create an IAM user with access keys for the application/CI"
Wrong. → IAM role (for EC2/ECS/Lambda) or OIDC federation (for GitHub Actions / GitLab).
🚩 "Use a Lambda scheduled hourly to check compliance"
Almost always wrong. → AWS Config rule (managed or custom) is the purpose-built tool.
🚩 "Write a Lambda to detect CloudFormation drift"
Wrong. → CFN Drift Detection + EventBridge schedule + SNS.
🚩 "Copy EBS snapshots cross-region with Lambda"
Wrong. → AWS Backup cross-region copy or DLM with copy schedule.
🚩 "Use OpsWorks for configuration management"
Almost always a distractor. → SSM Run Command + State Manager + Patch Manager.
🚩 "Inspector Classic" / "Macie Classic"
Both deprecated. → Use Inspector v2 and the current Macie.
🚩 "Use SCP to GRANT users permission"
Wrong by definition. SCPs only restrict; you still need IAM allow.
🚩 "Hard-code the API key / DB password"
Always wrong. → Secrets Manager (rotating) or SSM Parameter Store SecureString.
🚩 "Store secrets in S3 with bucket policy"
Wrong. → Secrets Manager. S3 doesn't give you rotation, versioning of secrets, or cross-account resource policies as cleanly.
🚩 "Open Security Group to 0.0.0.0/0 for testing"
Security trap. → Use scoped IPs, VPC endpoints, or SSM Session Manager.
🚩 "Disable encryption to fix the issue"
Always wrong. Disabling encryption is never the correct fix.
🚩 "Allow public access on RDS during deployment"
Wrong. → CodeBuild in VPC mode with subnet/SG access.
🚩 "Create separate pipeline per environment"
Usually wrong. → Single pipeline with parameterized stages / CodePipeline V2 variables / multiple deployment groups.
🚩 "Bake new AMI for every config change"
Wrong. → Use SSM Parameter Store / AppConfig for runtime config; AMI for code.
🚩 "Run cron job on EC2 to push metrics"
Outdated. → CloudWatch Agent (push) or EMF (embedded metric format in logs).
🚩 "Create a Lambda glue between SQS/Kinesis and target"
Often unnecessary now. → EventBridge Pipes with optional filter + enrichment.
🚩 "Use CloudWatch Events" (in 2024+ question)
Still works but outdated naming. → Prefer EventBridge in modern answers.
🚩 "Bake CodeBuild logs into the AMI"
Nonsense. → CloudWatch Logs / S3 for build logs.
🚩 "Manually edit the production stack template"
Never. → Change Sets + pipeline approval. Manual edits become drift.
🚩 "Use S3 Cross-Region Replication for DR of a database"
Wrong scope. CRR is for objects. → Aurora Global DB / DynamoDB Global Tables for DB DR.
🚩 "Multi-AZ" presented as a DR strategy
Multi-AZ = HA within a region, NOT DR. Question wants multi-region.
🚩 "Use Macie for malware / container scanning"
Wrong scope. Macie = S3 data classification. → GuardDuty Malware Protection / Inspector v2.
🚩 "Use GuardDuty to detect software vulnerabilities"
Wrong scope. GuardDuty = threats. → Inspector v2 for CVEs.
🚩 "AWS Config for who-did-what audit"
Wrong. Config = resource state. → CloudTrail for API/user audit.
🚩 "CloudTrail to detect resource state drift"
Wrong. CloudTrail = API calls. → Config rules / CFN drift detection.
🚩 "Use S3 lifecycle to immediately move to Glacier"
There's a minimum 30-day storage requirement before transitions for some classes. Check the constraint.
🚩 "Run Athena query every 5 minutes to alert"
Wrong cost/latency. → CW Logs Metric Filter for real-time.
🚩 "Increase ALB idle timeout to 1 hour to fix dropped requests"
Symptom-fix. → Use ASG lifecycle hook + target deregistration delay.
🚩 "Use Beanstalk to manage 100 accounts"
Wrong scope. → Organizations + StackSets + Control Tower.
🚩 "Encrypt secrets with envelope encryption using your own Python"
Reinventing the wheel. → Use Secrets Manager / KMS directly.

⚖️ "Sounds right but isn't" — common red herrings

Red herring · "Use AWS Glue to schedule jobs"
Glue is for ETL on data. For scheduled jobs use EventBridge Scheduler or Step Functions.
Red herring · "Use Lambda function URL to expose API"
Function URLs are simple but lack throttling/auth. For prod APIs use API Gateway with usage plans.
Red herring · "Use CloudFront to load-balance backend"
CloudFront caches + edge routes, but for actual L7 load balancing use ALB.
Red herring · "S3 + CloudFront as a DR strategy for RDS"
Mismatched primitives. → Aurora Global or RDS cross-region read replica.
Red herring · "EventBridge as primary message bus for ordered processing"
EventBridge doesn't guarantee order. → SQS FIFO or Kinesis for ordering.
Red herring · "Kinesis for low-volume notifications"
Kinesis has shard cost / setup overhead. → SNS / SQS for low volume.

🧩Question Pattern Templates — recognize the stem in < 10s

DOP-C02 recycles ~30 stem shapes. Memorize the pattern → know the answer category before reading all options.

"A company has multiple AWS accounts managed by AWS Organizations. They want to [enforce X / deploy Y / monitor Z] across all accounts, including new accounts as they are added…"
Pattern P-01 · Multi-Account Governance
→ CloudFormation StackSet with service-managed permissions, deployed to the Org root or OU, auto-deployment ON.
Why: auto-deployment is the only way to cover future accounts without re-running anything. Self-managed StackSets miss this.
"The team wants to ship traffic gradually to a new version of a [Lambda / ECS service], with validation at each step and auto-rollback on alarm…"
Pattern P-02 · Safe Traffic Shifting
→ CodeDeploy with Canary/Linear config + pre/post traffic hooks (Lambda) + linked CloudWatch alarm for auto-rollback.
"…with the least operational overhead…"
Pattern P-03 · Least Ops
→ Pick the option with the most managed services and fewest custom Lambdas/EC2.
Heuristic: count "custom"/"Lambda function"/"cron"/"script" tokens in each answer — fewer wins.
"Continuously evaluate that [resources] meet [requirement] and automatically remediate when they don't…"
Pattern P-04 · Compliance + Auto-Remediation
→ AWS Config rule (managed or custom) → SSM Automation document as remediation action.
"The build needs to access [private RDS / internal service / on-prem]…"
Pattern P-05 · CodeBuild VPC
→ CodeBuild project with VPC configuration (subnets + SG). For on-prem: VPN/DX + DNS resolution.
"Deploy artifacts from account A to account B securely…"

"Centrally archive logs from all accounts to a single immutable store…"

→ CW Logs Subscription Filter → Kinesis (central) → Firehose → S3 with Object Lock + KMS.
"Detect when [an unauthorized API call / config change / threat] occurs and react automatically…"

→ EventBridge rule (filter on event source/detail) → target = Lambda / SSM Automation / SNS / Step Functions.
"…with RTO < X minutes across two regions…"

→ RTO seconds = Active/Active; RTO minutes = Warm Standby; RTO hours = Pilot Light. Pair with Route 53 health checks.
"Run patching on EC2 fleet monthly with controlled blast radius…"

"Production stack must be protected from accidental deletion…"

"Need to enable [a feature / config] for X% of users without deploying code…"

"Logs must be searchable in real time AND archived cheaply for 7 years…"

"Compliance team wants a continuous compliance score across the Org…"

"Run a scheduled task at scale across timezones with retries and DLQ…"

④ CloudFormation StackSets — service-managed vs self-managed

Service-managed (preferred for Org-wide)

  • StackSets uses AWS Organizations trust — no roles to create per account.
  • Target the Org root or specific OUs.
  • Enable Auto-deployment so newly-joined accounts receive the stack automatically.
  • Optional delegated administrator account (so you don't have to use the management account).
  • Cannot target the management account itself.

Self-managed (legacy / custom)

  • You create two IAM roles:
    • AWSCloudFormationStackSetAdministrationRole in the admin account
    • AWSCloudFormationStackSetExecutionRole in every target account, trusting the admin role
  • Used when accounts are not in an Organization, or for backward compatibility.
  • No auto-deployment to new accounts (you must add them manually).

💡 Account filters when targeting an OU

When deploying to an OU, choose: NONE = all accounts under the OU; INTERSECTION = only accounts in your supplied list and in the OU; DIFFERENCE = OU accounts except your list; UNION = OU accounts plus your list (rare).

⑤ Auto Scaling Lifecycle Hooks — the drain/bootstrap pattern

Pending:Wait (launch)

  • Instance is launched but not yet InService.
  • Use to install custom software, fetch config, register with external systems.
  • EventBridge rule on EC2 Instance-launch Lifecycle Action → SSM Run Command / Lambda.
  • Caller invokes complete-lifecycle-action with CONTINUE (or ABANDON to terminate).

Terminating:Wait (scale-in)

  • Instance is being terminated; pauses to drain.
  • Combine with ALB target-group deregistration delay for connection draining.
  • Run a final SSM Run Command to flush logs, deregister from Consul/Eureka, etc.
  • Heartbeat default 1 h, max 48 h. Use RecordLifecycleActionHeartbeat to extend.

⑦ ECS Task Placement Strategies & Constraints

Strategies (how to choose containers)

  • binpack — packs tasks onto fewest instances (cost). Field: memory or cpu.
  • spread — even distribution across attribute:ecs.availability-zone / instanceId / custom attribute. Resilience.
  • random — random placement (rare).

Constraints (hard rules)

  • distinctInstance — no two tasks of this service on the same EC2 (single-tenant per host).
  • memberOf — cluster query expression (e.g., attribute:ecs.instance-type =~ t2.*).
  • Combine: spread across AZ + binpack within AZ for cost-and-resilience.

Don't confuse with EC2 placement groups (cluster / spread / partition) — those are hardware-locality groups for VMs, not container-scheduling rules.
